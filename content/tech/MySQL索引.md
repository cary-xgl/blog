## 索引

为什么数据库更喜欢 BTree 这类结构，而不是红黑树。

还是磁盘 IO 的问题。

红黑树虽然也是平衡树，但层数会比较深。数据一多，查一次就要一路往下走很多层。BTree 和 B+Tree 每个节点能放更多关键字和指针，树会矮很多，更适合按页去读磁盘数据。这样一次 IO 能带上更多内容，整体会更划算。

## 数据结构

### BTree

BTree 本身是平衡搜索树。

如果一个节点里有 `n` 个关键字，那它就会有 `n + 1` 个孩子。

几个基本点：

- 节点里的关键字按非降序排
- 每个内部节点会有多个孩子指针
- 所有叶子节点深度相同
- 每个节点里的关键字数量有上下界

BTree 的高度虽然也是 `O(logn)`，但因为一个节点里能放很多关键字，所以实际高度会比红黑树低不少。

插入时可能遇到满节点，这时候要分裂。BTree 的处理思路不是等走到底了再回头拆，而是沿途遇到满节点就先拆开。这样真正插入时，父节点一般已经不是满的了。

删除会更麻烦一点，因为可能会遇到关键字数量已经贴下限的节点。这时候要么跟兄弟节点借，要么直接合并。

### B+Tree

B+Tree 可以看成 BTree 的变种。

和 BTree 比，区别主要在这几处：

- `n` 个关键字对应 `n` 个子节点
- 数据都放在叶子节点
- 叶子节点之间会串起来，方便范围查找
- 内部节点更像索引层，主要拿来导航

数据库最后更偏 B+Tree，也是因为这个。

数据都放在叶子节点，内部节点就能塞更多索引项，树会更矮；而叶子节点串起来以后，范围查找和顺序扫描也会更顺。

## 随笔

MySQL 的索引是在存储引擎层实现的，不是在 server 层。

所以就算多个存储引擎都支持同一种索引类型，底下的实现也不一定一样。

InnoDB 用的就是 B+Tree 索引。

存储可以粗一点分成主存和外存。

- 主存一般就是内存
- 外存一般就是磁盘

机械磁盘比内存慢很多，原因也很直接，盘片要转，磁头要移动。

所以数据库才会尽量按页去读数据，想办法把一次 IO 的收益拉高。

## 索引存储的两种结构

### hash索引

如果字段建的是 hash 索引，存进去的其实是 hash 值和指向数据行的指针。

限制也很明显：

- 不能拿来排序
- 不支持范围查找
- 不支持最左前缀这类部分匹配
- 还要处理 hash 冲突

但如果场景刚好合适，性能会很高。

InnoDB 里还有自适应 hash 索引。

### BTree索引

MySQL 里更常见的还是这类树索引，底下就是前面那套 B+Tree 结构。

## 索引的几种类型

### 主键索引

主键索引就是建在主键上的索引。

InnoDB 里主键索引默认是聚簇索引，一张表也只能有一个。

聚簇索引的意思是，叶子节点里直接放的就是整行数据。所以按主键查的时候，找到叶子节点基本就拿到数据了。

### 非主键索引

#### 普通索引

普通索引允许重复值。

#### 唯一索引

唯一索引不允许重复值。

#### 多列索引

多列索引也叫联合索引。

几个常见点：

- 不按最左列查，很多时候就用不上
- 一旦中间碰到范围查询，右边列的利用率会明显下降
- 顺序合适的话，也能顺手拿来做 `order by`

#### 全文索引

#### 覆盖索引

比如执行：

```sql
select c_name where c_key = 'e';
```

如果只在 `c_key` 上建了索引，那通常会先去索引树里找到 `c_key`，再拿到主键信息，回主键索引里把整行数据取出来，这一步就是回表。

如果根据 `c_key` 查 `c_name` 的场景很多，就可以建联合索引 `(c_key, c_name)`。

这样有些查询就不用回表了，直接在联合索引里把事情做完。`explain` 里也更容易看到 `Using index`。


## 什么时候考虑用 hash 索引

hash 索引在 `MEMORY` 引擎里会显式用到。

它底下其实就是一个 hash 表。比如对单列 `A` 建 hash 索引，可以理解成先算出 `hash(A) = x`，表里存的就是：

| x | 指向行的指针 |
| --- | --- |
| y | 指向行的指针 |

限制也很明显：

- 不存具体数据，只存 hash 值和行指针，所以最后还是要顺着指针把行取出来
- 不是按索引值顺序存的，所以不能拿来排序
- 不支持部分列匹配，因为 hash 是对整段值一起算的
- 不支持范围查找，只适合等值比较
- 有 hash 冲突时，底下还得顺着链表逐个比

限制虽然多，但场景对了，性能提升会很明显。

比如数据仓库里一些典型的等值查找场景，或者某些字段很长、重复度又不高的情况，比如 URL，也可能会考虑 hash 这条路。

InnoDB 里还有一种自适应 hash 索引。它发现某些索引值访问特别频繁时，会基于 B+Tree 在内存里再建一层 hash 来加速热点访问。这是自动做的，也可以配成关闭。

## 索引失效的场景

比如有个联合索引：`A B C`

能比较好用上索引的场景：

- 全值匹配：`A = x and B = x and C = x`
- 最左匹配：`A = x`
- 第一列范围匹配：`A like 'x%'`
- 第一列精确匹配，第二列范围匹配

容易失效或者只部分生效的场景：

- 不是从最左列开始查，比如 `B = x` 或 `C = x`
- 跳过了中间列，比如 `A = x and C = y`，这时通常只会用到前面那部分
- 前面某一列已经用了范围查询，后面的列一般就很难继续用上索引

所以联合索引里，列顺序很重要。
