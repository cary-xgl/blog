## SSH SSL
SSH（secure shell）: 加密的网络传输协议，可在不安全的网络环境中提供安全的传输环境；
SSH通过在网络中创建安全隧道来实现SSH客户端与服务器之间的连接[2]。SSH最常见的用途是远程登录系统

### SSH VS SSL 
SSL/TLS做的事情大体和SSH相似 都是用来对数据进行加密已经对用户身份进行鉴权，但依旧有几个不同点，下面罗列一下
SSL一般用来在客户端与服务端进行连接，而SSH一般用来建立在不同机器上不安全的远程连接上；
SSL依赖于公钥的基础，就是说他必须验证传过来的CA证书的合法性，而SSH之间无需如此 SSH主机只需建立密钥对并分发给不同的用户即可，无需对CA证书做校验;
SSL基于应用层与传输层之间的套接字层（Socket层：用来对传输层的TCP或其他传输层协议进行包装，而应用层无需了解具体的细节实现），SSH则是基于应用层的shell;
SSL基于SSL/TLS证书进行工作，SSH基于网络信道的传输工作；
SSL有效防止中间人攻击，SSH防止DNS/IP欺骗等；

### SSH端口转发
#### 本地端口转发：
比如远程机器R 端口3306有个mysql服务，现在我们想访问他
顾名思义就是把本地的请求转发到远程端口上，
ssh -L 3307:localhost:3306 root@R.IP
#### 远程端口转发:
通常本地主机是没有公网IP的 他与同一网络中的主机共享同一IP，所以外部机器想访问我们服务是无法访问的，所以我们可以让他访问主机IP，然后将请求转发到本地端口
ssh -R 3306:localhost:3307 root@R.IP
#### 动态转发：
远程云主机R运行了多个服务，分别使用了不同端口，本地主机A需要访问这些服务。
ssh -D localhost:2000 root@R.IP
会将所有发送给本地的请求都转发远程主机上，由远程主机去发起对应的请求

## https是如何工作的
首先https协议基于一个可信任的证书工作，并且是非对称加密和对称加密的结合（因为非对称加密对两端来说每次的加解密代价太大，所以我们只用于建立连接，真正的传输数据的过程还是用对称加密）
可以有效防止中间人攻击（除非中间人也是一个可信的证书..）
### 完整的https流程如下：
客户端向服务端请求建立连接
服务端向客户端返回一个公钥和证书信息
客户端验证证书信息是否为可信任的证书（经过CA机构认证过的）如果可信任
客户端生成一个用于加密数据的对称加密密钥 并用公钥加密发给服务端
服务端用私钥解密这样就可以用客户端的密钥进行加解密数据了

## http status
**100-199**：表示临时响应并需要请求者继续执行操作的状态代码。
**200**： 成功并把资源返回回去
**202**： 已接受，但服务器可能尚未处理完成，比如内部开启了一个异步的线程处理
**204**： 服务器已成功处理，但并未返回任何内容
**301**： 永久重定向 说明请求的资源已经被移动到了由 Location 头部指定的url上 并且标准要求浏览器在收到该响应并进行重定向时(GET HEAD)不应该修改http method和body
**302**： 重定向状态码表明请求的资源被暂时的移动到了由Location 头部指定的 URL 上。浏览器会重定向到这个URL，同样进行重定向时（GET HEAD）不应该修改http method和body
**400**： bad request 语法无效 服务器无法理解 可能是url错误等
**401**： 未授权的操作 需要进行身份校验
**403**： forbidden 服务器拒绝此请求 
**404**： 服务器找不到需要的资源，可能资源已被删除
**500**： 服务器内部错误
**502**： bad gateway 表示作为网关或代理角色的服务器，从上游服务器（如tomcat）中接收到的响应是无效的 一般是web服务器不可用
**503**： 服务器尚未处于可以接受请求的状态
**504**： 请求超时 表示作为网关或代理角色的服务器无法在规定的时间内获得结果，一般是web服务器响应超时

### 302 vs 307 同 301 vs 308
当发送重定向请求的时候，307 状态码可以确保请求方法和消息主体不会发生变化。如果使用 302 响应状态码，一些旧客户端会错误地将请求方法转换为 GET：也就是说，在 Web 中，如果使用了 GET 以外的请求方法，且返回了 302 状态码，则重定向后的请求方法是不可预测的；但如果使用 307 状态码，之后的请求方法就是可预测的。对于 GET 请求来说，两种情况没有区别

### tcp
可靠数据传输(rdt)
- rdt1.0是基于理想情况下的协议，假设所有信道都是可靠的，没有比特位的翻转，没有数据包的丢失与超时，所以rdt1.0的传输功能就是 发送方发送数据，接收方接受数据。
- rdt2.0增加了3种新机制：1.错误检验 2.接收者反馈接受信息（ACK,NAK）3.重传机制。在运输层对应用层的数据进行打包处理时，新增checksum（校验和），从而接收端可以对其数据包进行检验，如果正确，返回ACK，发送者继续发送下一个数据包；如果不正确，返回NAK，发送者重传数据。 总结：增加ack和nak
- rdt2.1 解决了 如果接收方返回ack或者nak出错的重传机制
- rdt2.2 在2.1基础上去掉了nak，改用有序号的ack，这样接收方只需返回最后一个确认收到的ack序号即可
- rdt3.0在rdt2.2的基础之上处理了数据包丢失的情况，增加了计时器的机制，如果在RTT时间段内，发送方没有接收到反馈信息，那么发送方默认数据包已经丢失了，会自动重传。往返延迟（rtt）
- 但3.0由于是单个分组的传输,所以如果网络节点较长的话，那么等待的时间就会很长，造成由于网路协议浪费了大量的带宽，再次基础上采用流水线协议改进，使得一次可以传输多个分组
    - go back n(回退n重传)，一次发送n个数据报，等待最后一个包超时重传的时间如果接收方没有给予确认，那么需要把n个数据报再次重传
    - selective repeat(选择重传协议)： 发送方发送n个数据报，接收方单独确认每个数据报，如果其中一个没有收到，那么发送方只需发送这一个数据报即可

 #### 路由选择算法
 路由：按照某种指标找到一条从源节点到目标节点的【较好】路径
 
-  迪杰斯特拉 单源节点最短路径，缺点是，每个节点都要不断算，可能会导致现在A路径最快，下一次就不是了，因为所有网络都从这个路径走
- 距离矢量路由算法：定期测量，定期更新 dx(y) = min(c(c,v) + d(v)) 只需要邻居发送给我他到目标节点的最短路径，不知道的就无限大，所以，需要很多次迭代才能达成最优解，不断迭代不断更新 分布式更新，每个节点不断更新当前信息，最终会收敛为最短路径 （缺点是如果某条路径不可达，可能会形成环路，很多次迭代之后才能使其他节点知道某个节点路径不可达）
