## load data

mysql可以通过load data提高速度（文件-->数据库） ---mysqlimport
通过SELECT ... INTO OUTFILE 把数据库中的数据导入到文件之中；

插入的时候如果时一条一条INSERT 则相对来说是最慢的；
如果通过INSERT VALUE list的方式批量插入则会比单条插入更快一些；
而当通过Load data 的方式则更快，大约比直接插入快20倍左右

mysql列是有默认值的，当要插入的列与默认值不同的时候才把这列作为插入条件，这减少了mysql必须做的解析，可以提高执行的速度；

## DDL&DML&DCL

DML（data manipulation language）数据操纵语言
具体的为SELECT UPDATE DELETE INSERT等对数据直接操作的语句

DDL（database definition language）数据库定义语言
比如创建表用到的一些sql语句 CREATE 或者对列进行操作的一些 DROP ALTER等

DCL（Database Control Language）数据库控制语言
一般用来更改角色或数据库用户比如 GRANT DENY等语句

## 数据结构
### BTree
**平衡搜索树**
节点x包含n个关键字，那么x有n+1个孩子

**BTree定义：**
m阶 = 2t-1
节点x n个关键字并且以非降序排放 x.leaf(是否为叶子节点)
每个内部节点x 包含n+1个指向孩子的指针
每个叶子节点具有相同的深度 即树高h相同
每个节点所包含的关键字有上界和下界 成为BTree的最小度数（t）
    除了根节点的其他节点至少有t-1个关键字，如果树非空，根节点至少有一个关键字
    每个节点至多包含2t-1个关键字（2t个孩子），当一个节点恰好具有2t-1个关键字时，称该节点是满的

高度虽然也是O(lgn),但相比红黑树高度随着最小度数的增加而降低

**插入操作（可能会遇到满节点的情况，此时需要分裂节点），而BTree采用的并不是从上往下找到实际要插入的满节点才进行分裂，而是只要沿途中遇到满节点就进行分裂，这样，每当要分裂节点时，就能确保父节点不是满节点！**
三个方法：分裂方法（节点满）（父节点保证不为满节点 <2t-1）
                其中分裂操作中间节点提升到父节点，其他分裂成两个t-1的节点即可
             根节点开始（满则特殊判断分裂，增加树高的唯一途径，只能从上层增加）
             非满节点递归（上面两个方法保证节点的非满性）
    
 **删除操作（可能会遇到最少节点的情况，此时需要对此节点进行合并或向上层借节点），BTree采用的并不是从上往下找到实际要删除的节点才进行分裂，因为可能需要合并，此时需要向父节点借关键字，父节点如果在临界节点，就会再进行递归，这样，每当要删除节点的关键字时，就能确保父节点不是最少（t-1）个节点！**
删除k关键字操作：
    x节点 
    y节点：x k元素左子节点
    z节点：x k元素右子节点
    三种情况
    删除叶子节点的关键字（关键字节点大于t-1）：直接删除
    删除内部节点：
        情况1：y节点关键字>=t，则找到y最右前驱（k'）并提升至原来k关键字的位置,然后对子树递归
        情况2：寻找z节点关键字>=t,则找到z最左前去（k'）并提升，然后对字数递归
        否则: y z都只有t-1个关键字，合并这两个节点（父节点关键字一定>t-1）
    删除叶子节点关键字（关键字等于t-1）:
        叶子节点x,父节点xp ,兄弟节点xb，k元素在x中，父节点分割元素xpk
        情况1：其中一个兄弟节点xb的关键字>t-1,提升xb中其中一个元素（最左或最右）为xpk,xpk降至k元素位置
        情况2：兄弟节点都为t-1，此时挑选一下进行合并，父节点xpk也加入，此时合并后的节点为2t-2
    
### B+Tree
Btree的一种变种
**B+Tree定义（对比BTree来说）:**
n个关键字存储n个子节点（BTree存储n+1个）
B+Tree数据都存在叶子节点上，BTree则内部节点和叶子节点也会存储
B+Tree每个叶子节点都存有相邻节点的单向指针（从小到大）
同一个关键字会在不同节点出现，因为只有叶子节点会存储数据，所以最终指向的是叶子节点，而由于BTree数据存储在每一个节点上，所以BTree上关键字不重复

## 随笔

mysql索引是在存储引擎层实现的，而不是服务器层，不同存储引擎的索引工作方式也不一样，所以即使多个存储引擎支持同一种类型的索引，其底层的实现也不一定相同

BTree索引 B+Tree索引 InnoDb使用B+Tree索引

存储：主存和外存
主存一般为主板上的存储介质（硅），又称为内存
外存一般是磁盘 磁盘（硬盘，软盘（已被u盘替代，几乎无人使用））

（机械磁盘）磁盘的组成：
盘片（可以有多个） 
主轴（盘片绕主轴） 
磁道（在盘片上，有多个磁道）
读写磁头（由磁臂控制）

由于磁盘有机械运动（盘片的旋转 磁臂的移动）的部分，所以比内存慢的多，为了摊还机械移动所花的等待时间，磁盘会一次存取多个数据项，信息被分成一系列大小相等的在柱面内连续出现的位页面

## 索引存储的两种结构
### hash索引
字段name 存储为hash索引的时候 会进行hash函数的运算，存入【hash值（有序的），指向数据行的指针】
hash索引的限制：
hash索引无法用于排序（排序需要额外耗费时间？）
不支持部分索引查找，A,B两列建立索引，则hash函数会对此两列进行运算，仅用一个字段实际上并不会走hash索引
不支持范围查找
需解决hash冲突

优点：一旦找到适合hash索引的场合，则性能提升显著

## 索引的几种类型
### 主键索引（默认主键是聚簇索引，且一张表最多创建一个）
顾名思义，建立在主键上的索引
采用bTree存取
查找记录的时候如果是根据主键 进行where条件的查询，则会在B+Tree上先找到此主键，然后去叶子节点拿数据即可
聚簇索引：叶子节点直接存储实际数据（不用根据地址去磁盘中取）

对于多列索引来说：

#### 覆盖索引
对于普通的索引来说 假设select c_name where c_key = 'e';
如果我们有建立在c_key上的索引，那么此时的一个查找流程应该是先去此索引树中找到key,然后此节点存取了主键信息，然后在去主键索引里查找，此操作被称为回表，用explain之后会发现extra列中无相关信息
而后如果根据key查找name的频率很高，那么我们就可以建立联合索引（c_key, c_name)，
用explain之后会发现extra列用了use index（这样查找的时候不会有回表的操作，在联合索引中就把事情办了）
