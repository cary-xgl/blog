## MySQL 间隙锁

间隙锁可以共存，多个事务同时锁住同一段区间也不冲突。

它锁的不是某一行，而是一段区间。比如下面这张表，`id` 是主键：


| id | name | value |
| --- | --- | --- |
| 5 | tt | 5 |
| 10 | tt | 10 |
| 15 | 15 | 15 |
| 20 | 20 | 20 |
| 25 | 25 | 25 |


这时候如果想插入一条 `id = 8` 的数据，锁住的不是 `5-10` 这段区间，而是这条准备插入的位置。

但如果是对 `id = 8` 这条记录做更新或者删除，因为这条记录本身不存在，InnoDB 就会去锁住离它最近的那段区间，也就是 `5-10`。

Next-Key Lock 可以理解成间隙锁和行锁放在一起，锁住的区间一般是 `(5, 10]`，左开右闭。

## MySQL 意向锁

MySQL 里有表锁，比如：

- `LOCK TABLE xxx READ`
- `LOCK TABLE xxx WRITE`

读锁会挡住别的事务修改表数据，写锁会挡住别的事务读写。

InnoDB 还有行锁。行锁里常见的是：

- 共享锁：这一行只能读
- 排他锁：这一行可以读写，别人不能动

表锁和行锁放在一起时，就会碰到一个问题。

比如事务 A 锁住了表里某一行，只让它读，不让它写。接着事务 B 又想给整张表加写锁。如果 B 真加成功了，那它理论上就能改表里的任意一行，这和 A 手里的行锁就是冲突的。

数据库怎么判断这个冲突？

最直接的办法是：

- 先看表上有没有表锁
- 再看表里每一行有没有被行锁锁住

问题就在第二步，真这么做代价太高，等于要把整张表扫一遍。

意向锁就是拿来解决这个问题的。

有了意向锁之后，事务 A 在加行锁之前，会先在表上挂一个意向共享锁。这样事务 B 过来想加表写锁时，一看表上已经有意向共享锁，就知道这张表里已经有行锁了，直接阻塞就行，不用再扫整张表。

> 意向锁是数据库自己加的。我们平时写 SQL 只是在申请行锁，表上的意向锁会由 InnoDB 自动补上。
