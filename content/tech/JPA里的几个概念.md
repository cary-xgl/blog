## JPA、Spring Data JPA、Hibernate

这三个东西经常一起出现，但不是一层。

- `JPA` 是规范
- `Hibernate` 是对这套规范的一种实现
- `Spring Data JPA` 是更上面一层的封装，底下通常还是会落到 `Hibernate`

所以平时说“用了 JPA”，很多时候真正跑起来的其实是 `Hibernate`。

## SQL 注入

`Spring Data JPA` 这套写法，本身就比较天然地避开 SQL 注入。

核心原因不复杂，就是参数和 SQL 结构是分开的，底层走的是预编译。SQL 在编译阶段就已经确定了结构，后面传进去的参数只是参数，不会再去改执行逻辑。

所以这类注入，主要是破坏 SQL 编译过程；一旦编译已经结束，后面再传进去的东西更多只是普通输入。

## 一级缓存和二级缓存

一级缓存只在当前持久化上下文里生效，而且默认关不掉。

有一点比较容易漏：一级缓存命中通常是按主键来的。

比如第一次已经查出了一个实体，第二次如果还是按主键查，能直接命中一级缓存；但如果换成其他字段去查，就算这个字段本身有唯一索引，一般也还是会重新打到数据库。

二级缓存是全局层面的，对不同事务都能生效，不过它不是默认就一定开，要额外配置，也有不同策略可以选。

## 事务提交时为什么会自动更新

比如下面这段代码，在事务里执行时，就算不手动调 `save`，事务提交时也可能会自动发更新 SQL：

```java
User user = userRepository.find(id);
user.setName("newName");
// userRepository.save(user);
```

原因是 `JPA` 会做脏检查。

查出 `user` 之后，当前上下文里会保留这份实体，同时还会留一份快照。后面你改的是当前上下文里的对象，快照本身不动。等事务提交时，JPA 会比较这两份数据；如果发现不一致，就会生成更新 SQL。

所以这里不调 `save`，更新通常也会生效。

不过代码里要不要显式写 `save`，有时候还是看团队习惯。如果接手的人对 JPA 不熟，显式写出来可读性会更高一点。

## 几种对象状态

- 瞬时态：对象刚创建出来，不在持久化上下文里，数据库里也没有
- 持久态：对象已经进入持久化上下文，数据库里也有对应数据
- 游离态：数据库里有，但当前对象已经不在持久化上下文里

比较常见的变化是：

- 新对象 `save` 之后，会从瞬时态变成持久态
- 事务结束后，对象脱离当前上下文，就会变成游离态
- 游离对象重新进入持久化上下文后，又会回到持久态

## 继承关系的几种策略

`JPA` 里常见的继承策略主要有三种。

### `TABLE_PER_CLASS`

```java
@Inheritance(strategy = InheritanceType.TABLE_PER_CLASS)
```

每个子类各有一张表，公共字段每张子表里都会存一份。

- 好处：查某个具体子类时比较直接，只查自己的表就行
- 问题：如果要把所有子类一起查出来，SQL 会比较多
- 适合：主结构比较稳定，变化主要靠子类扩展

### `JOINED`

```java
@Inheritance(strategy = InheritanceType.JOINED)
```

父类单独一张表，公共字段放父表，子类各有自己的表，通过主键关联。

- 好处：公共字段维护起来更舒服，加字段时只需要动父表
- 问题：查完整对象时会有不少 join，子表一多，查询会比较重
- 适合：实体经常调整，维护成本比查询性能更重要

### `SINGLE_TABLE`

```java
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
```

所有子类都落到同一张表里。

- 好处：查整类数据最快，单表查询最直接
- 问题：字段约束会比较别扭，尤其是不同子类字段差异大时，很难做严一点的非空限制
- 适合：更看重存储和查询简单，不太在意表设计的整洁度

## `@Transactional(readOnly = true)`

这个注解对 `Hibernate` 也有影响。

当事务是 `readOnly = true` 时，`Hibernate` 的 `FlushMode` 会变成 `manual`，默认情况下本来是 `auto`。这会让事务轻一点，读请求的执行速度通常也会更快。

`FlushMode` 常见的几个值：

- `manual`：不自动刷新，需要手动触发
- `commit`：事务提交时再刷新
- `auto`：默认模式，按需要刷新
- `always`：每次查询前都刷新
