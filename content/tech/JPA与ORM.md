## jpa 一二级缓存
一级缓存会在当前上下文生效，一级缓存默认不可取消；
- 一级缓存生效的条件：比如第一次查询出来一个实体，那么第二次再查询此实体的时候需要通过主键查询才能命中一级缓存，如果是通过其他字段（即使是唯一索引的字段）也不会命中缓存，会重新去数据库中查询

二级缓存在全局生效，所有事务都生效（可配置多种二级缓存的策略，也可以不配置）

## jpa的事务提交自动更新
比如有以下代码块（包含在事务中）,那么当事务提交的时候user会被自动更新，即使未调用save方法，但代码中还是推荐加上save方法，因为代码看上去会可读性高一些（对应jpa还不太熟悉的接手的人）
原因：jpa在查询user的时候内存中会保存两份数据，一份保存在一级缓存中；另一份保存到快照空间中，其中我们做修改的操作是修改的缓存中的对象，快照空间中的是不动的，这样一级缓存中的如果做过修改，那么就会和快照空间中的不一致，这样当事务提交的时候jpa会去校验快照空间中的和一级缓存中的实体，如果发现不一致，则会自动生成更新语句并更新对象（隐式的调用了更新语句）
```java
User user = userRepository.find(id);
user.setName("newName");
## userRepository.save(user);
```

## jpa的几种状态
瞬时态: 对象刚创建出来的状态，不在一级缓存中，也不在数据库中
持久态：新对象save之后，游离态变为持久态，数据库中和持久化上下文中都存在
游离态：对象在数据库中存在，但是不在一级缓存中，此时对象处于游离态，当事务提交之后对象由持久态变为游离态，重新save之后，对象变为持久态

## jpa 关于继承关系

以insight的标签体系为例，目前是采用join策略，目前的业务场景下，其实查询全部的标签还挺常见的，所以需要权衡join和table_per_class（多个单条sql）的权重，感觉可能是table_per_class更快？？（待测试）

目前jpa有三种策略：
- @Inheritance(strategy = InheritanceType.TABLE_PER_CLASS): 这种策略是每种分类都会有一张表来保存,公共的属性子类也会都保存一份
    - 优点：对于查询单个分类下的数据很友好，只需要查询对应的子表即可；对于外键关联的属性，比如人群里面含有的标签，那其实就没法加外键，因为并没有一个统一的表，其实更符合insight目前的设计思路，即外键的属性通过代码来维护，数据库不保存外键，在我看来这是优点
    - 缺点：如果查询所有的标签,那需要执行很多sql
    - **适合场景：** 业务层面上主表设计好之后几乎无变动，变动只是作为扩展类出现（不过业务上的变动谁说的准呢emmm）
- @Inheritance(strategy = InheritanceType.JOINED)： 这种策略是采用关联关系保存，每个子类一张表，其中父类会保存公共的属性，主类子类通过主id join
    - 优点：对于公共属性的抽离很友好，因为只需要在一张主表里新加字段即可，如果是采用table_per_class 这种策略，那需要每张表都加属性；
    - 缺点：查询很慢，因为比如标签查询所有表需要做大量的join，join操作是效率低下的（不推荐三张表以上的join），标签体系子表众多
    - **适合场景：** 可能会经常有变动的实体（可维护性好，对于业务设计上其实比较好，因为业务是不可预估的）
- @Inheritance(strategy = InheritanceType.SINGLE_TABLE)：这种策略是所有子类都会保存到同一张表里
    - 优点：查询所有的数据很快，因为是单表查询
    - 缺点：不能对字段进行非空校验，比如有些子类中的字段，其他子类并不需要，所以无法对属性做一些非空限制，比如标签的所有type字段都维护到一张表里，看着很乱
    - **适合场景：** 我觉得最好不要使用这种策略，因为这种虽然对数据库存储和查询很友好，但业务是展现给coder看的，所以目前没想到合适的场景

## orm框架简介
object-relation mapping 对象关系映射
对象：java中一切皆对象（面向对象编程）
关系：关系型数据库中实体和实体之间都是关联的

这样能从中找到一个映射关系来用面向对象编程的方式来操作数据库

## 优点
代码量少（因为一些通用的东西已经能满足大部分日常使用了，并且这部分已经被封装过）
数据模型只定义一次，有利于重用（比如采用继承的方式啥的）

## 缺点
sql优化不好做
对于复杂查询，orm框架的表现能力比较差

## 常见的orm框架

### mybatis
mybatis: 半自动框架，可以自己定义数据模型，映射关系，但是sql语句一般是要自己编写，而其他orm框架一般都会定义常用的函数方法等

优点是：可以优化sql，对于性能以及复杂的查询来说较友好

缺点是：需要手动编写sql,效率低下，并且可能出现sql注入的问题
>sql注入：比如页面上有个用户登录框，如果后台是select * from user where username = '{}' and password = '{}', 那么如果知道了用户名，页面上输入aa and 1=1 --，因为--是mysql的注释键，所以会把password的校验去掉，就可能实现了无需密码的登录

### spring data jpa and hibernate
jpa其实是一种规范,在这个规范上hibernate遵守并实现了，而spring data jpa是更上层的抽象，在hibernate的基础上封装了一层

spring data jpa天然防sql注入
>jpa防止sql注入：因为Jpa是采用预编译的
在使用PreparedStatement执行SQL命令时，命令会带着占位符被数据库进行编译和解析，并放到命令缓冲区。然后，每当执行同一个PreparedStatement语句的时候，由于在缓冲区中可以发现预编译的命令，虽然会被再解析一次，但不会被再次编译。
而SQL注入只对编译过程有破坏作用，执行阶段只是把输入串作为数据处理，不需要再对SQL语句进行解析，因此解决了注入问题。
因为SQL语句编译阶段是进行词法分析、语法分析、语义分析等过程的，也就是说编译过程识别了关键字、执行逻辑之类的东西，编译结束了这条SQL语句能干什么就定了。而在编译之后加入注入的部分，就已经没办法改变执行逻辑了，这部分就只能是相当于输入字符串被处理。

>mysql的查询执行

相比于mybatis的使用，更容易复用，因为jpa是通过元数据模型来查询的，所以查询语句更容易复用，而mybatis是自己写sql，可能经常写出大量多表join的语句，此时不利于维护，但是查询速度更快更容易优化

## jpa的n+1问题 
举例，查询所有的用户，findAll() ,当jpa调用时，假设用户内存在的oneTomany（比如标签）（默认懒加载）和manyToOne（默认饿加载）（比如用户组）这种都是非懒加载的，那么当查询出来所有的用户（一条sql）的同时，会分别对每个用户查询用户组（n个用户查询n次，标签这种n个用户也是会查询n次对应的标签），所以这样看来只有要一条是存在外键关联的情况，jpa会生成n条语句，而比如用户组这种内部也可能作为其他表的外键关联表存在，会在级联的递归下去查询

改善：所有的外键实体都设置成懒加载，这样需要的时候才去查询，而不是比如上面的可能这次其实不需要标签的信息，但还是查询出来了，浪费了n次查询甚至更多，但本质上依然没有改变n+1条语句的情况

解决n+1问题的方案：entitygraph 以上面的例子查询的时候会把用户组作为user的查询join，所以单看用户表其实只会生成一条sql,如果用户组内也有其他外键，也可以级联的设置entitygraph来实现（待确认）

## transaction注解对hibernate的影响
当transaction的字段readonly设置为true时，此时hibernate的flushmode会变成manual(默认是auto),事务的执行速度可以大大加快
>flushmode枚举值：
>- manual: 内部不会刷新session，只能手动刷新session
>- commit：只有事务提交的时候才会刷新缓存
>- auto：每次查询都会与本地缓存进行比较，如果发现过期则刷新缓存，否则不刷新
>- always：每次查询都会刷新缓存

## DDD
### 几种模型的比较
领域驱动设计： 

>血： domain object的model层的概念

- 失血模型：所有业务逻辑由service层处理，model层只提供get set方法，会导致service层逻辑太重(只有service和model层)，一般不采用
- 贫血模型：相对于失血模型来说 多了一层dao层，大多数业务场景都采用此模型来设计，dao层可以封装一些基础的查询方法，service层进行组合调用
- 充血模型：相比于贫血模型，更加看中了domain model层的概念，弱化service层的使用，service层仅用来封装一些少量的逻辑，并提供事务的支持，并且是与领域层进行交互；其中model层会包含与dao层的交互
- 胀血模型：此模型取消了service层，只保留了dao层和model的概念，更少见了，事务都在model层进行处理，对domain object进行充分利用

其中一般采用贫血和充血两种模型，并且日常以贫血为主，其实充血模型才更符合面向对象变成的概念，充血模型使得对象是高内聚的，而贫血模型，对象仅充当一个载体的作用

>为什么贫血模型流行：
>- 适合场景比较简单，基础的curd操作
>- 充血模型的设计比较复杂，一开始就要尽可能考虑好针对的对象有哪些行为，要暴漏，要封装哪些操作；而贫血模型我们只要定义好数据载体之后，有新的业务可以放到service层进行，不需要进行过多的设计
>- 概念的接受问题

充血模型是尽可能利用对象 去进行某些行为的操作，并且领域模型不应该依赖于dao层和数据库进行通信，这样会对单测造成不必要的复杂度（因为相当于与持久化层做了一层交互），而像hibernate这种提供了透明的持久化机制（会在事务提交前，检查session中的数据是否与缓存的一致，如果不一致，会有一条更新语句会生成），所以是dao层的实现 对domain层进行了隐式的调用，这样有个好处是dao层是一个可插拔式的，domain层的单测无需对其他层进行依赖

### 基于事件的几种处理

#### spring服务内部的轻量级事件通信
发布事件： ApplicationEventPublisher 直接调用publishEvent(object) 发布即可

监听事件：使用EventListener 或者 TransactionalEventListener注解即可监听，其中TransactionalEventListener可以增加对事件事务的支持，如果事件涉及到事务，则可以针对事务做特殊的处理（比如几种策略，事务提交后执行，事务提交前执行等），并可以配合async异步执行

#### 多服务间的事件总线
生产事件：通过数据库层记录事件的发布，消费等（spring event也可以增加持久化层的支持），由于需要和数据库通信，所以天然支持事务，可以定制化一些事务提交后执行的策略，并通过定时任务+接口来实现事件的发布

事件的发布：可以定制化一些策略比如通过mq来实现多服务间的通信（具体合适的发布订阅场景，待补充）

消费事件：其他服务通过绑定事件对应的routekey等方式进行事件的消费
