## 线程的几种状态
先把这几个状态分清，不然后面看锁、线程池和中断都容易混。

- `NEW`：线程对象刚创建出来，还没调用 `start()`
- `RUNNABLE`：已经可以被调度了。Java 这里把“就绪”和“运行中”都放在 `RUNNABLE` 里，不再细分
- `BLOCKED`：通常是在等 `synchronized` 的 monitor 锁
- `WAITING`：线程主动等别人唤醒，比如 `wait()`、`join()`、`park()`
- `TIMED_WAITING`：和 `WAITING` 类似，只是多了超时条件，比如 `sleep()`、`wait(timeout)`、`join(timeout)`
- `TERMINATED`：线程执行完了，或者因为异常退出了。这个状态结束后，线程不能再 `start()` 一次

可以先记一个简化版：

```text
NEW
  -> start()
RUNNABLE
  -> 等 monitor 锁        => BLOCKED
  -> 主动 wait/join/park  => WAITING
  -> sleep/wait(timeout)  => TIMED_WAITING
  -> run() 结束           => TERMINATED
```

有个容易混的点是 `BLOCKED` 和 `WAITING`。

- `BLOCKED` 更像是“想进临界区，但锁没拿到”
- `WAITING` 更像是“我自己先停下来，等别人叫我”

## 线程的中断 interrupt
线程中断本质上是一个标记位，不是强制杀线程。

也就是说，调用 `interrupt()` 之后，并不是线程立刻停掉，而是告诉它：“该收了，别再往下跑了。”

常用的 3 个方法：

- `interrupt()`：给目标线程打一个中断标记
- `isInterrupted()`：查看目标线程当前是不是中断状态，不会清掉标记
- `interrupted()`：查看当前线程是不是中断状态，同时会把标记清掉

这里最容易记混的是后两个：

- `isInterrupted()` 是查别人，或者查自己，但不改状态
- `interrupted()` 是查当前线程，并顺手把标记清掉

如果线程正卡在这些可中断的方法里：

- `sleep()`
- `wait()`
- `join()`
- `Condition.await()`
- 一些可中断的 I/O / lock 操作

那它收到中断后，通常不会继续傻等，而是直接抛出 `InterruptedException`。同时，中断标记也会被清掉。

这也是为什么很多代码里在 `catch (InterruptedException e)` 之后，会补一句：

```java
Thread.currentThread().interrupt();
```

因为异常抛出来的时候，中断标记已经被清掉了。如果你还希望上层知道“这个线程其实被中断过”，就得自己再补回去。

再补一个容易漏的点：

- `synchronized` 等锁的过程不可中断
- `ReentrantLock.lock()` 默认也不可中断
- `ReentrantLock.lockInterruptibly()` 才是可中断的
- `tryLock(timeout, unit)` 在等待过程中也可以响应中断

所以如果你担心死锁或者长时间卡死，`lockInterruptibly()` 和带超时的 `tryLock()` 会更灵活一点。

## 线程的挂起与恢复
`suspend()` 和 `resume()` 现在基本可以直接当成历史遗留。

它的问题不在“老”，而在危险。

`suspend()` 会把线程直接挂起，但它不会帮你释放已经拿到的锁。这样如果线程 A 拿着锁被挂起了，线程 B 又刚好等这个锁，B 就永远过不去。如果恢复 A 的逻辑又恰好在 B 后面，那就直接僵住了。

所以这两个方法被废弃不是风格问题，是很容易把程序挂死。

## 线程池
线程池解决的其实不是“怎么开线程”，而是“怎么别把线程开炸了”。

### 为什么要用线程池

- 降低线程频繁创建和销毁的成本
- 任务来了可以直接复用已有线程，响应更快
- 可以限制并发量，不至于资源一路冲到失控
- 方便统一做监控、命名、拒绝策略、异常处理

如果完全不用线程池，最常见的问题有两个：

- 线程创建太频繁，系统开销很大
- 没有任何节流手段，高峰期很容易把内存、CPU、下游依赖一起拖垮

### `ThreadPoolExecutor` 在做什么

`Executor` 这一层提供的是一个很朴素的思路：任务提交和任务执行解耦。

也就是你只管把任务交进去，至于线程怎么创建、什么时候复用、队列怎么排、任务满了怎么办，这些交给线程池。

核心参数先记这几个：

- `corePoolSize`：核心线程数
- `maximumPoolSize`：最大线程数
- `workQueue`：任务队列
- `threadFactory`：线程工厂，通常用来起名字
- `handler`：拒绝策略

补一句，`workQueue` 不一定是无界的。实际项目里反而更常见的是显式选一个有界队列，不然任务堆太多的时候更难收场。

来了一个任务之后，线程池大概按这个顺序处理：

```text
任务提交
  |
  |-- workerCount < corePoolSize
  |      -> 直接创建核心线程执行
  |
  |-- 否则尝试入队
  |      -> 队列没满：先放队列
  |
  |-- 队列也满了
  |      -> workerCount < maximumPoolSize
  |             -> 再创建非核心线程执行
  |
  |-- 线程也到上限了
         -> 走拒绝策略
```

这个流程里最容易误判的地方是：  
**不是任务一来就直接开线程开到 `maximumPoolSize`。**

通常会先尽量用核心线程，再入队，队列扛不住了才继续扩线程。

### 线程池的状态

- `RUNNING`：接收新任务，也处理队列里的旧任务
- `SHUTDOWN`：不再接收新任务，但会把队列里的任务跑完
- `STOP`：不接新任务，不处理队列任务，还会尝试中断正在执行的线程
- `TIDYING`：任务和线程都清得差不多了，准备收尾
- `TERMINATED`：彻底结束

日常最常碰到的是前 3 个，后两个更像收尾状态。

### 空闲线程怎么回收

空闲线程不是线程池手动“杀掉”的，更准确地说，是线程池让它退出工作循环，不再持有引用，后面再由 JVM 回收。

这里和 `keepAliveTime` 关系很大：

- 当线程数超过核心线程数后，多出来的那些线程如果空闲太久，就会被回收
- 如果允许核心线程超时，核心线程也可以回收

### 拒绝策略

常见的拒绝策略有：

- `AbortPolicy`：直接抛异常
- `DiscardPolicy`：静默丢弃
- `DiscardOldestPolicy`：丢掉队列里最老的任务，再尝试提交当前任务
- `CallerRunsPolicy`：让提交任务的线程自己执行

`CallerRunsPolicy` 看起来温和，但它其实会把压力反推给上游线程。用得好是削峰，用不好就是把调用链一起拖慢。

### 线程池怎么配，最容易踩什么坑

最常见的坑不是不会配，而是只盯着线程数，不盯队列和任务类型。

- 最大线程数太小：高峰期扛不住，任务开始堆，最后拒绝
- 队列太长：表面上没拒绝，实际上延迟被吞进队列里，上游一样超时
- 最大线程数太大：线程切换和资源竞争反而会拖慢系统
- 任务里有阻塞调用：比如远程调用、数据库、磁盘 I/O，这种线程池不能只按 CPU 核数去估

所以线程池配置不是单看一个数字，而是一起看：

- 任务是 CPU 密集还是 I/O 密集
- 单个任务执行时长
- 峰值流量有多高
- 下游能不能扛住并发

### 关于 `@Async`

`@Async` 如果不显式指定线程池，实际用哪个执行器，和 Spring 版本、配置、上下文都有关系。  
这块最好别赌默认值，直接自己配一个名字明确的线程池，再通过 `@Async("xxxExecutor")` 指过去。

这样至少有几个好处：

- 线程名清楚，排查问题容易
- 不会和别的异步任务混用一个默认池
- 核心线程数、队列长度、拒绝策略都能自己控住

## 线程vs进程
这个问题很基础，但面试里也很常问。

- 进程是程序的一次执行过程，资源分配的粒度更大
- 线程是进程里的执行单元，调度更轻量

线程之间共享进程里的大部分资源，比如堆、方法区、文件描述符这些；也正因为共享，线程之间才更容易互相影响。

可以粗一点记：

- 进程更像“房子”
- 线程更像“房子里同时干活的人”

房子之间通常隔得更开，房子里的人协作更方便，但也更容易互相踩脚。

## 父子线程数据共享
这块通常会想到 `InheritableThreadLocal`。

它的作用是：创建子线程时，把父线程里那份线程本地变量拷一份过去。

线程构造时本身就有这个开关：

```java
private Thread(ThreadGroup g, Runnable target, String name, long stackSize, AccessControlContext acc, boolean inheritThreadLocals) {
 pass;
}
```

最后那个 `inheritThreadLocals` 就是在控制，要不要把父线程的 `InheritableThreadLocal` 带给子线程。

```java
if (inheritThreadLocals && parent.inheritableThreadLocals != null) {
    // 这里会复制父线程的数据
    this.inheritableThreadLocals =
        ThreadLocal.createInheritedMap(parent.inheritableThreadLocals);
}
```

这里有个容易误会的点：  
它不是父子线程实时共享一份数据，更像是**子线程创建时拷一份过去**。

所以：

- 如果你传的是不可变值，比如 `String`、`Integer`，那就是带一份快照过去
- 如果你传的是对象引用，那父子线程看到的是同一个对象，改对象内部属性时彼此能感知

`ThreadLocalMap` 内部大概可以粗看成这样：

```text
Thread
  └─ ThreadLocalMap
       ├─ Entry(key = ThreadLocal弱引用, value = 值)
       ├─ Entry(...)
       └─ Entry(...)
```

其中 key 是对 `ThreadLocal` 的弱引用，主要是为了降低内存泄漏的风险。  
但它不是说“用了弱引用就一定没事”，因为 value 还在，线程本身如果一直活着，这些值还是可能留很久。所以用完 `ThreadLocal` 最稳的习惯还是 `remove()`。

相关代码大概是这样：

```java
ThreadLocalMap getMap(Thread t) {
    return t.threadLocals;
}

void createMap(Thread t, T firstValue) {
    t.threadLocals = new ThreadLocalMap(this, firstValue);
}
```

之前项目里有个场景比较典型：  
异步线程要往不同 app 发广播请求，请求时要带上父线程里的 host 信息。这个时候如果 host 在任务开始前就已经确定，而且后面不会再变，其实没必要强上 `InheritableThreadLocal`，直接在新线程里重新设置一次就够了。

换句话说：

- 只需要把上下文带过去一次，用显式传参或者手动 `set()` 往往更稳
- 只有你明确需要“创建子线程时自动继承一份上下文”，`InheritableThreadLocal` 才更合适
