> Java中的线程与线程池相关...
<!--more-->

## 线程的几种状态

- `NEW`：线程对象刚创建出来，还没调用 `start()`
- `RUNNABLE`：运行中。Java 这里把“就绪”和“运行中”都放在 `RUNNABLE` 里，不再细分
- `BLOCKED`：通常是在等 `synchronized` 的 monitor 锁
- `WAITING`：线程主动等别人唤醒，比如 `wait()`、`join()`、`park()`
- `TIMED_WAITING`：和 `WAITING` 类似，只是多了超时条件，比如 `sleep()`、`wait(timeout)`、`join(timeout)`
- `TERMINATED`：线程执行完了，或者因为异常退出了。这个状态结束后，线程不能再 `start()` 一次

```text
NEW
  -> start()
RUNNABLE
  -> 等 monitor 锁        => BLOCKED
  -> 主动 wait/join/park  => WAITING
  -> sleep/wait(timeout)  => TIMED_WAITING
  -> run() 结束           => TERMINATED
```

`BLOCKED` 和 `WAITING` 比较容易混：

- `BLOCKED` 是想进去，但锁还没拿到
- `WAITING` 是自己先停下来，等别人唤醒

## 线程的中断 interrupt
中断本质上是一个标记位，不是强行把线程停掉。

调用 `interrupt()` 之后，线程不会立刻死，只是收到一个信号，后面怎么处理还得看它自己。

常用的 3 个方法：

- `interrupt()`：给目标线程打一个中断标记
- `isInterrupted()`：查看目标线程当前是不是中断状态，不会清掉标记
- `interrupted()`：查看当前线程是不是中断状态，同时会把标记清掉

如果线程正卡在这些可中断的方法里：

- `sleep()`
- `wait()`
- `join()`
- `Condition.await()`
- 一些可中断的 I/O / lock 操作

那收到中断后，一般会直接抛出 `InterruptedException`，同时把中断标记清掉。

所以写代码时会在 `catch (InterruptedException e)` 之后补一句：

```java
Thread.currentThread().interrupt();
```

因为异常抛出来时，中断标记已经没了。如果还想让上层感知到这次中断，就要自己补回去。

还有个容易忽略的点：

- `synchronized` 等锁的过程不可中断
- `ReentrantLock.lock()` 默认也不可中断
- `ReentrantLock.lockInterruptibly()` 才是可中断的
- `tryLock(timeout, unit)` 在等待过程中也可以响应中断

所以遇到可能长时间等锁的场景，`lockInterruptibly()` 和带超时的 `tryLock()` 更好用。

## 线程的挂起与恢复
`suspend()` 和 `resume()` 现在基本不用了，比较容易出事。

`suspend()` 会直接把线程挂起，但不会释放已经拿到的锁。要是线程 A 拿着锁被挂起，线程 B 又在等这把锁，B 就会一直卡住。如果恢复 A 的逻辑又依赖 B 往下走，程序就僵住了。

所以这两个方法被废弃。

## 线程池
线程池是用来管理线程的。

### 为什么要用线程池

- 降低线程频繁创建和销毁的成本
- 任务来了可以直接复用已有线程，响应更快
- 可以限制并发量，不至于资源一路冲到失控
- 方便统一做监控、命名、拒绝策略、异常处理

如果不用线程池，常见问题如下：

- 线程创建太频繁，系统开销很大
- 没有任何节流手段，高峰期很容易把内存、CPU、下游依赖一起拖垮

### `ThreadPoolExecutor`

`Executor` 这一层本质上是拆开提交任务和执行任务。

调用方只管把任务交进去，线程怎么建、什么时候复用、队列怎么排、满了怎么办，这些都交给线程池。

核心参数：

- `corePoolSize`：核心线程数
- `maximumPoolSize`：最大线程数
- `workQueue`：任务队列
- `threadFactory`：线程工厂，通常用来起名字
- `handler`：拒绝策略

`workQueue` 不一定是无界的。实际项目里更常见的反而是有界队列，不然任务一多，问题只是从“被拒绝”变成了“排队排到超时”。

任务进来之后，大概按这个顺序处理：

```text
任务提交
  |
  |-- workerCount < corePoolSize
  |      -> 直接创建核心线程执行
  |
  |-- 否则尝试入队
  |      -> 队列没满：先放队列
  |
  |-- 队列也满了
  |      -> workerCount < maximumPoolSize
  |             -> 再创建非核心线程执行
  |
  |-- 线程也到上限了
         -> 走拒绝策略
```

这里有个常见误区：不是任务一来就把线程开到 `maximumPoolSize`。

正常顺序还是先用核心线程，再尝试入队，队列顶不住了才继续扩线程。

### 线程池的状态

- `RUNNING`：接收新任务，也处理队列里的旧任务
- `SHUTDOWN`：不再接收新任务，但会把队列里的任务跑完
- `STOP`：不接新任务，不处理队列任务，还会尝试中断正在执行的线程
- `TIDYING`：任务和线程都清得差不多了，准备收尾
- `TERMINATED`：彻底结束

平时比较容易碰到的是前 3 个。

### 空闲线程怎么回收

空闲线程不是线程池手动 Kill 的，更准确地说，是线程池让它退出工作循环，后面再交给 JVM 回收。

主要和 `keepAliveTime` 相关：

- 当线程数超过核心线程数后，多出来的那些线程如果空闲太久，就会被回收
- 如果允许核心线程超时，核心线程也可以回收

### 拒绝策略

常见的拒绝策略有：

- `AbortPolicy`：直接抛异常
- `DiscardPolicy`：静默丢弃
- `DiscardOldestPolicy`：丢掉队列里最老的任务，再尝试提交当前任务
- `CallerRunsPolicy`：让提交任务的线程自己执行

`CallerRunsPolicy` 实际上是把压力往调用方推。用得好能起到削峰的作用，用不好会把上游一起拖慢。

### 线程池参数配置

线程池如果只盯线程数，不看队列和任务类型，容易出问题。

- 最大线程数太小：高峰期扛不住，任务开始堆，最后拒绝
- 队列太长：表面上没拒绝，实际上延迟被吞进队列里，上游一样超时
- 最大线程数太大：线程切换和资源竞争反而会拖慢系统
- 任务里有阻塞调用：比如远程调用、数据库、磁盘 I/O，这种线程池不能只按 CPU 核数去估

线程池选择参数的时候可以考虑：

- 任务是 CPU 密集还是 I/O 密集
- 单个任务执行时长
- 峰值流量有多高
- 下游能不能扛住并发

### 关于 `@Async`

`@Async` 如果不显式指定线程池，最后到底走哪个执行器，和 Spring 版本、配置、上下文都有关系。

这块最好别使用默认值，直接配一个名字明确的线程池，再通过 `@Async("xxxExecutor")` 指过去。

这样做的好处：

- 线程名清楚，排查方便
- 不会和别的异步任务混用一个默认池
- 核心线程数、队列长度、拒绝策略都能自己控制

### 常见创建方式

一般不太建议直接用 `Executors` 提供的那些快捷方法。不是说不能用，而是参数都藏在里面，后面别人接手时不太直观，也更容易把队列、线程数这些关键点忽略掉。

#### `newFixedThreadPool`

`Executors.newFixedThreadPool(n)` 会创建一个核心线程数和最大线程数都等于 `n` 的线程池。

- 队列默认是 `LinkedBlockingQueue`
- 队列本质上接近无界，默认上限非常大
- 线程数固定，适合把并发量卡在一个范围里

它的问题也很直接：线程数虽然控住了，但任务堆积是没控住的。高峰期如果任务一直进，队列可能越排越长，最后把内存顶满。

#### `newSingleThreadExecutor`

这个线程池的核心线程数和最大线程数都只有 `1`，队列同样是 `LinkedBlockingQueue`。

适合那种必须串行执行的任务，比如顺序生成记录、顺序刷状态这类场景。

#### `newCachedThreadPool`

这个线程池核心线程数是 `0`，最大线程数接近 `Integer.MAX_VALUE`，`keepAliveTime` 默认 `60s`，队列是 `SynchronousQueue`。

它的特点是几乎不排队，来一个任务就尽量找线程接。没有空闲线程就继续创建。

好处是轻任务、突发任务处理起来很快，问题是线程数没上限，任务一多就可能一路膨胀。

#### `newScheduledThreadPool`

`Executors.newScheduledThreadPool(n)` 适合定时和周期任务。

- 核心线程数是 `n`
- 队列是 `DelayedWorkQueue`
- 底下是按最近执行时间排序的

所以每次拿出来的，基本都是最该先执行的那个任务。

#### 自定义 `ThreadPoolExecutor`

项目里更常见的，还是直接自己 new 一个 `ThreadPoolExecutor`：

```java
new ThreadPoolExecutor(
    coreSize,
    maxSize,
    keepAliveTime,
    unit,
    queue,
    threadFactory,
    rejectedHandler
)
```

这样线程数、队列、线程名、拒绝策略都清清楚楚，后面排查问题也方便。

### `FixedThreadPool` 和 `CachedThreadPool`

这两个都可能把内存打爆，只是方向不一样：

- `FixedThreadPool` 更容易把问题堆到队列里
- `CachedThreadPool` 更容易把问题堆到线程数里

一个是任务太多，另一个是线程太多，本质上都可能 OOM。

### 线程池怎么提交任务

- `submit()`：有返回值，返回 `Future`
- `execute()`：没有返回值

如果你后面要拿执行结果、感知异常或者取消任务，通常就会用 `submit()`。

### `keepAliveTime`

`keepAliveTime` 主要影响的是那些超过核心线程数的空闲线程。

线程空闲以后，会去队列里等任务。如果等到超时还没拿到任务，就会退出工作循环，后面交给 JVM 回收。

如果把核心线程超时也打开，那核心线程也能按这套规则回收。

### 拒绝策略怎么落地

常见的拒绝策略有：

- `AbortPolicy`：直接抛 `RejectedExecutionException`
- `DiscardPolicy`：直接丢
- `CallerRunsPolicy`：交给调用线程自己跑

业务里如果真走到拒绝，一般不会只满足于“丢了就算了”。更常见的是自定义策略，把线程池状态、任务信息、告警这些一起带上。

之前项目里更常见的做法，是让当前线程先兜底执行，同时打一封告警邮件出来。

### 线程池会把内存打爆吗

会。

常见就两种：

- 队列太长，任务一直堆
- 线程太多，线程对象和栈空间一起把内存顶满

所以线程池不是“用了就安全”，参数没控好，一样能把系统拖垮。

## 线程vs进程

- 进程是程序的一次执行过程，资源分配的粒度更大
- 线程是进程里的执行单元，调度更轻量

线程之间共享进程里的大部分资源，比如堆、方法区、文件描述符这些。也正因为共享，线程之间更容易互相影响。

形象记忆：

- 进程像房子
- 线程像房子里同时干活的人

房子之间隔得更开，房子里的人协作方便，但也更容易互相踩脚。

## 父子线程数据共享
这块一般会想到 `InheritableThreadLocal`。

它的作用是在创建子线程时，把父线程里的线程本地变量拷一份过去。

线程构造时本身就有这个开关：

```java
private Thread(ThreadGroup g, Runnable target, String name, long stackSize, AccessControlContext acc, boolean inheritThreadLocals) {
 pass;
}
```

最后这个 `inheritThreadLocals`，控制的就是要不要把父线程里的 `InheritableThreadLocal` 带给子线程。

```java
if (inheritThreadLocals && parent.inheritableThreadLocals != null) {
    // 这里会复制父线程的数据
    this.inheritableThreadLocals =
        ThreadLocal.createInheritedMap(parent.inheritableThreadLocals);
}
```

它不是父子线程实时共享同一份数据，更像是子线程创建时拷了一份。

所以：

- 如果传的是不可变值，比如 `String`、`Integer`，那就是一份快照
- 如果传的是对象引用，那父子线程看到的还是同一个对象，改对象内部属性时彼此能感知

`ThreadLocalMap` 内部可以粗看成这样：

```text
Thread
  └─ ThreadLocalMap
       ├─ Entry(key = ThreadLocal弱引用, value = 值)
       ├─ Entry(...)
       └─ Entry(...)
```

其中 key 是对 `ThreadLocal` 的弱引用，主要是为了降低内存泄漏风险。

但这不等于用了弱引用就一定没事，因为 value 还在。线程如果一直活着，这些值还是可能留很久。所以 `ThreadLocal` 用完之后，`remove()` 还是要记得调。

相关代码大概是这样：

```java
ThreadLocalMap getMap(Thread t) {
    return t.threadLocals;
}

void createMap(Thread t, T firstValue) {
    t.threadLocals = new ThreadLocalMap(this, firstValue);
}
```

之前项目里碰到过一个场景：异步线程要往不同 app 发广播请求，请求时要带上父线程里的 host 信息。这个时候如果 host 在任务开始前就已经确定，而且后面不会再变，其实没必要上 `InheritableThreadLocal`，直接在新线程里重新设一次就够了。

所以这块不要套：

- 只需要把上下文带过去一次，用显式传参或者手动 `set()` 往往是更好的选择
- 只有明确需要“创建子线程时自动继承一份上下文”，`InheritableThreadLocal` 才更合适
