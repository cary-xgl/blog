## 线程的几种状态
初始状态（NEW）：实现runnable 或者 继承Thread类可以得到一个线程类 new一个实例出来，线程就进入了初始状态
运行状态（RUNNABLE）：包含就绪（Ready）状态和   运行中（RUNNING）状态，调用线程的start方法，此线程进入就绪状态，但就绪状态是说有资格运行，但cpu调度程序可能并不会调度到
    运行中是指线程调度程序从上下文线程池中挑选一个可用的线程执行任务，等待当前线程时间片用完调度程序调用yield方法使线程重新进入就绪状态
阻塞状态（Blocked）:阻塞线程是指线程阻塞在比如进入synchronized关键字修饰的方法或代码块(获取锁)时的状态
等待状态（Waiting）:处于这种状态下的线程cpu不会分配时间片，他们要显式的被唤醒，否则会处在无限期等待的过程中
超时等待（Timed_WAITING）:和上面相比较只是不会无限期等待，到达超时时间他们会自动唤醒
终止状态（TERMINATED）: 线程正常执行完成或者出现异常终止的状态，已经处于终止状态的线程不能被start

## 线程的中断 interrupt
线程的中断有个状态位来标识：true则线程被中断，中断的结果是死亡还是等待新的任务或者继续运行至下一步取决于这个程序本身，程序可以时不时检测状态位来判断线程是否应该向下进行下去或是怎么样，他并不像stop一样会中断一个正在运行的线程

中断一个线程只是为了引起该线程的注意，被中断线程可以决定如何应对中断

* interrupt(): 中断此线程，或者由管理线程发起中断线程的操作
* interrupted(): 判断线程是否处于中断状态，并且会清楚状态位（置为false）,所以第二次发起判断的时候一定是false
* isInterrupted(): 判断线程是否处于中断状态,幂等的，不会清除状态位

如果一个线程处于了阻塞状态（如线程调用了thread.sleep、thread.join、thread.wait、以及可中断的通道上的 I/O 操作方法后可进入阻塞状态），则在线程在检查中断标示时如果发现中断标示为true，则会在这些阻塞方法（sleep、join、wait、1.5中的condition.await及可中断的通道上的 I/O 操作方法）调用处抛出InterruptedException异常，并且在抛出异常后立即将线程的中断标示位清除，即重新设置为false。抛出异常是为了线程从阻塞状态醒过来，并在结束线程前让程序员有足够的时间来处理中断请求

>synchronized在获锁的过程中是不能被中断的，意思是说如果产生了死锁，则不可能被中断。与synchronized功能相似的reentrantLock.lock()方法也是一样，它也不可中断的，即如果发生死锁，那么reentrantLock.lock()方法无法终止，如果调用时被阻塞，则它一直阻塞到它获取到锁为止。但是如果调用带超时的tryLock方法reentrantLock.tryLock(long timeout, TimeUnit unit)，那么如果线程在等待时被中断，将抛出一个InterruptedException异常，这是一个非常有用的特性，因为它允许程序打破死锁。你也可以调用reentrantLock.lockInterruptibly()方法，它就相当于一个超时设为无限的tryLock方法

## 线程的挂起与恢复
suspend resume （挂起和恢复，不被推荐使用Deprecated），其本质和sleep一样，也不会释放资源，但sleep会自动醒，而suspend则需要和resume配合，这就造成了一个问题；
假设有两个线程，其中一个执行到比如system.out.println挂起了，此时out对象是临界资源，被线程A所持有并挂起；而线程B也需要这个对象，可能打印完才会执行其他代码再唤醒A,这样就造成了死锁，所以不被推荐使用！

## 线程池
为什么要使用线程池：

* 降低资源消耗：通过池化技术重复利用已创建的线程，降低线程创建和销毁造成的损耗。
* 提高响应速度：任务到达时，无需等待线程创建即可立即执行。
* 提高线程的可管理性：线程是稀缺资源，如果无限制创建，不仅会消耗系统资源，还会因为线程的不合理分布导致资源调度失衡，降低系统的稳定性。使用线程池可以进行统一的分配、调优和监控。
* 提供更多更强大的功能：线程池具备可拓展性，允许开发人员向其中增加更多的功能。比如延时定时线程池ScheduledThreadPoolExecutor，就允许任务延期执行或定期执行。

如果不用线程池会发生什么，或者说线程池解决的问题是什么

* 频繁申请/销毁资源和调度资源，将带来额外的消耗，可能会非常巨大。
* 对资源无限申请缺少抑制手段，易引发系统资源耗尽的风险。
* 系统无法合理管理内部的资源分布，会降低系统的稳定性。

使用线程池不当可能会发生什么问题：

* 如果线程池最大核心数设置过小，而业务场景中可能会有突发流量激增的情况，这种情况下，阻塞队列很快就塞满了，所以就会造成大量的接口被拒绝访问，造成接口降级
* 队列设置过长，这样可能造成的情况是大量接口过来的任务在队列中堆积，如果是作为中间服务存在，那么可能会造成大量上游服务调用超时

代码中用到的线程池（比如分批）：@async注解如果不指定线程池会采用系统默认带的线程池（
core thread size = 8 ；max thread size 最大int值）, 相当于不限制线程的数量；但可以通过配置来控制线程数量，或者自定义线程池（可以获取当前系统的cpu，更好的评估线程的数量）

## 线程vs进程
进程是程序的一次执行过程，是基本的调度单位，并且要申请资源，比如cpu的占用时间，内存等，进程是操作系统的范畴，各进程不会相互影响；
而一个进程中可以有多个线程，并且多个线程共享一块进程的内存空间和资源使用，所以线程更小更轻量，但线程之间的调度因为是共享资源，所以可能会相互影响；

## 父子线程数据共享
使用InheritableThreadLocal

创建一个线程的时候，在默认的构造方法经传递有一个参数如下:
```java
private Thread(ThreadGroup g, Runnable target, String name, long stackSize, AccessControlContext acc, boolean inheritThreadLocals) {
 pass;
}
```
最后有个参数表示是否开启父子线程共享(并且父线程有数据的情况下才会共享)
```java
if (inheritThreadLocals && parent.inheritableThreadLocals != 
null) {
//内部是浅拷贝了一份，所以可以动态感知上层的变化
    this.inheritableThreadLocals =        ThreadLocal.createInheritedMap(parent.inheritableThreadLocals);
}

// 如果是InheritableThreadLocal<Integer> 这种，则无法感知，但如果是一个object，替换object里面的属性可以被子线程感知到，所以如果有这种动态感知的需求，需要自己包裹一层
```

threadlocalmap 内部的结构, 所以线程可以获取自己的所有线程本地变量，并赋值给子线程，  threadlocalmap内部是node节点存储的，key-> 引用了threadlocal结构, value -> 值，其中threadlocal是一个弱引用（下次gc发现此线程不在用了，则此key会被回收掉，防止了内存泄露），同时提供了一个方法判断key为null的时候，把value也回收掉（至于回收的时机待补充//todo）

ThreadLocalMap getMap(Thread t) {

/** * Create the map associated with a ThreadLocal. Overridden in * InheritableThreadLocal. * * @param t the current thread * @param firstValue value for the initial entry of the map */

    t.threadLocals = new ThreadLocalMap(this, firstValue);

使用异步线程进行 各个对接的app请求的广播请求的发送，此时需要获取父线程的host数据（不同的host 各app的host可能也不一样）并对应的请求的发送，此时需要上层把host传递进来，此种场景适用（目前采用的是获取父线程的变量在新线程里重新设置一次（基于ThreadLocal），此种场景下合适，因为父线程的host数据是不可变的，所以一次设置即可使用，不用动态变化，动态变化的话就要用InheritableThreadLocal了）
