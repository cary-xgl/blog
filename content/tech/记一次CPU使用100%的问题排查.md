> 循环里多查了一次配置，放到几十万条数据上就很明显。
<!--more-->

## 现象

`scheduler` 模块的数据资产扫描任务把 CPU 打满了。

这段扫描逻辑需要查全表，标签量级有几十万条。生成报表时，会遍历标签并判断目录展示规则。问题在于 `displayDirectory()` 这个函数会查询数据库里的配置项，如果把它放在循环判断里，每个标签都会查一次配置。

标签数量一上来，这个小查询就被放大成了高频数据库访问，CPU 很快被吃满。

当时问题代码大概是这样：

```java
  private String generateReport(List<Traits> traitsList) {
    if (CollectionUtils.isEmpty(traitsList)) {
      return "0,0";
    }
    Map<Boolean, List<Traits>> sumMap = traitsList.parallelStream()
        .collect(Collectors.partitioningBy(t -> TraitsType.DIRECTORY.equals(t.getType())));
    Map<Integer, List<Traits>> levelTraitsMap = traitsList.stream()
        .filter(t -> displayDirectory || t.getStatus().equals(Status.ENABLE))
        .collect(Collectors.groupingBy(t -> getTraitsLevel(traitsCommonService.getAncestors(t))));
    int maxLevel = levelTraitsMap.keySet().stream().max(Comparator.naturalOrder()).orElse(1);
    List<String> numbers = IntStream.rangeClosed(1, maxLevel)
        .map(level -> Optional.ofNullable(
            levelTraitsMap.get(level).stream()
                .filter(traits -> level == 1 || displayDirectory() ||
                    !TraitsType.DIRECTORY.equals(traits.getType()))
                .collect(Collectors.toList()))
            .map(List::size).orElse(0))
        .mapToObj(String::valueOf)
        .collect(Collectors.toList());

    return String.format("%d,%d,%s", sumMap.get(Boolean.TRUE).size(),
        sumMap.get(Boolean.FALSE).size(), String.join(",", numbers));
  }

  private Boolean displayDirectory() {
    return configCommonManager.getConfigBooleanValue("WEB_TRAITS_ASSETS_DISPLAY_DIRECTORY");
  }
```

## 排查过程

先进入容器，用 `top` 看进程 CPU 占用，找到异常的 Java 进程。这里假设进程 PID 是 `7`。

再用下面的命令看这个 Java 进程里各线程的 CPU 占用：

```bash
top -Hp 7
```

如果占用最高的线程 PID 是 `10`，需要先把它转成 16 进制。因为 `jstack` 里的线程 ID 用的是 16 进制：

```bash
printf "%x\n" 10
```

输出是 `a`，对应到 `jstack` 里就是 `0xa`。

然后查这个线程的堆栈：

```bash
jstack 7 | grep -C30 "0xa"
```

`-C30` 会把命中行前后 30 行一起打印出来，行数可以按情况调整。堆栈里定位到了 `displayDirectory()` 相关调用，再回到业务代码看，基本就能确认是循环里反复查配置导致的。

后面本地调试也复现了这个问题。

## 解决方案

这个配置在一次报表生成过程中不会变，所以没必要每次循环都查。

处理方式有两个：要么把 `displayDirectory()` 提到循环外，只查一次；要么给这个配置项加缓存。最后选了第一种，改动更小，也更直接。

修复后的代码如下：

```java
  private String generateReport(List<Traits> traitsList) {
    if (CollectionUtils.isEmpty(traitsList)) {
      return "0,0";
    }
    Map<Boolean, List<Traits>> sumMap = traitsList.parallelStream()
        .collect(Collectors.partitioningBy(t -> TraitsType.DIRECTORY.equals(t.getType())));
    Boolean displayDirectory = displayDirectory();
    Map<Integer, List<Traits>> levelTraitsMap = traitsList.stream()
        .filter(t -> displayDirectory || t.getStatus().equals(Status.ENABLE))
        .collect(Collectors.groupingBy(t -> getTraitsLevel(traitsCommonService.getAncestors(t))));
    int maxLevel = levelTraitsMap.keySet().stream().max(Comparator.naturalOrder()).orElse(1);
    List<String> numbers = IntStream.rangeClosed(1, maxLevel)
        .map(level -> Optional.ofNullable(
            levelTraitsMap.get(level).stream()
                .filter(traits -> level == 1 || displayDirectory ||
                    !TraitsType.DIRECTORY.equals(traits.getType()))
                .collect(Collectors.toList()))
            .map(List::size).orElse(0))
        .mapToObj(String::valueOf)
        .collect(Collectors.toList());

    return String.format("%d,%d,%s", sumMap.get(Boolean.TRUE).size(),
        sumMap.get(Boolean.FALSE).size(), String.join(",", numbers));
  }

  private Boolean displayDirectory() {
    return configCommonManager.getConfigBooleanValue("WEB_TRAITS_ASSETS_DISPLAY_DIRECTORY");
  }
```

## 复盘

循环里的逻辑要特别留意。单次看起来很轻的数据库查询，乘上几十万条数据以后就不是小事了。

这次问题更直接的处理是把循环里的公共值提前算好。类似的配置读取，如果调用链里复用很多，也可以考虑在配置层做缓存。
