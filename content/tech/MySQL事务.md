## 事务的四大特性

原子性（Atomicity）：一组操作要么一起成功，要么一起失败。

一致性（Consistency）：事务执行前后，数据都应该处在一个正确的一致状态里。拿转账举例，不管中间怎么折腾，A 和 B 的总金额不能变。

隔离性（Isolation）：多个事务同时跑时，彼此之间不能乱互相影响。

持久性（Durability）：事务一旦提交，对数据的修改就要落住。即使 MySQL 崩了或者重启了，这次提交也不能丢。

## 如果不考虑事务的隔离性，那么可能会发生哪些问题
前提：有两个事务 A 和 B

脏读：事务 A 改了一条数据，但还没提交，这时候事务 B 已经把这条未提交的数据读到了。如果后面 A 回滚了，那 B 刚才读到的就是脏数据。

不可重复读：事务 A 第一次读到一条数据后，中间事务 B 把这条数据改了并提交。A 再读一次，就发现前后不一样了。

幻读：和不可重复读有点像，只不过事务 B 不是改数据，而是插入了新数据并提交。这样事务 A 前后两次查同一个范围，结果条数可能会变。

## 事务的隔离级别
读到了别的事务未提交的数据（Read Uncommitted）：脏读、不可重复读、幻读都可能出现。

读到了别的事务已提交的数据（Read Committed）：脏读解决了，但后面两个问题还在。

可重复读（Repeatable Read）：不可重复读解决了。理论上还会有幻读，但后面的 MySQL/InnoDB 版本会结合 MVCC 和锁来处理掉一部分问题。这也是 MySQL 默认的隔离级别。

（待确认：修改单条数据是否是行级锁）是行级锁

串行化（Serialization）：最严格，所有问题都能解决，但事务基本就是排队执行了。

## Spring事务的传播机制
hibernate 从数据库里拉数据后，会在一级缓存 session 和快照里各放一份，改的时候其实改的是 session 里的那份。

`flush()` 时会去比对 session 和快照里的数据。如果不一样，就先同步到数据库，再更新快照。

对象在 hibernate 里的几种状态：

*     持久态：存入session的数据
*     游离态：不在session之中，未从数据库同步过来
*     瞬时态：new 出来的对象，不在session 数据库中也不存在

hibernate 的几种 FlushMode：

manual: 手动刷新，必须显式调 `flush()` 才会同步到数据库，适合 `@Transactional(readOnly = true)` 这类场景

commit: 事务提交时才 flush

auto：默认模式。查询前会比对 session 和快照，不一致时先 update，避免读到旧数据

always: 每次查询前都刷新

`@Query` 注解里的 `nativeQuery` 表示是不是原生 SQL。如果是，就直接写数据库 SQL；如果不是，写的是面向实体的查询，JPA 再帮你转成数据库能执行的 SQL。

传播机制：
required: 如果当前存在事务则加入 不存在则新创建一个（默认的选择）
supports: 如果当前有事务则加入当前事务，如果当前不存在事务那也不创建事务，以非事务执行
mandatory（强制的）:当前有事务则加入，无事务则抛出异常
requireds_new: 创建一个新的事务，如果当前session有事务则暂停当前事务
not_supported: 如果当前有事务则暂停当前事务 以非事务执行
never: 不支持事务，如果当前session有事务则抛出异常
nested（嵌套的）:当前不存在事务则新建一个，存在的话则作为子事务嵌套存在，这个子事务失败了外层事务可以选择回滚 也可以选择不回滚（catch掉即可），而如果选择Required，如果发生异常，那么不管catch掉还是干啥，外层事务都会回滚掉；如果嵌套子事务成功的话，会随外层事务一起提交  
开启嵌套子事务需要数据库引擎支持 savepoint，InnoDB 是支持的。因为 undo log 本身会记 undo_no，所以配合 savepoint 可以只回滚事务里的一部分。

## MVCC（基于多版本的并发控制）实现原理
注：和 MVCC 对应的是基于锁的并发控制。

MVCC 本质上是快照读。RR 下是第一次读数据时创建快照，不是事务一开始就建；RC 下则更偏向每次读取都拿新的视图。
>RC（Read Committed）和RR（Repeatable Read）隔离级别是利用consistent read view（一致读视图）方式支持的。 所谓consistent read view就是在某一时刻给事务系统trx_sys打snapshot（快照），把当时trx_sys状态（包括活跃读写事务数组）记下来，之后的所有读操作根据其事务ID（即trx_id）与snapshot中的trx_sys的状态作比较，以此判断read view对于事务的可见性。

ReadView表关键字段：
m_low_limit_id：读取的内容应该看不到任何trx_id>=此字段的事务值，此为高水位，为当前事务id+1,就是在此trx_id之后的事务都应该对此事务不可见
 m_up_limit_id：读取结果应查看所有严格小于此值（<）的trx id。换句话说，这是“低水位线”当前事务的最小值。由此可得在这中间的都是未提交的事务
 m_view_list(type = ReadView): 保存在上面区间的节点，struct结构，内部有pre next ReadView类型指针 这中间的事务需要根据事务的隔离级别来确定 不一定连续，因为可能有后来的事务会提交，先前的事务还没提交
 
 undo log日志：
undo log 里记录的是老版本数据。旧事务想读历史版本时，就顺着 undo 链往前找。

*  其中insert语句产生的undo log日志可以在事务提交后选择直接删除
*  update 和 delete则需要维护数据的版本关系

为了避免多个事务同时写 undo log 时打架，InnoDB 用回滚段来管这件事。

* rseg0预留在系统表空间ibdata中;
* rseg 1~rseg 32这32个回滚段存放于临时表的系统表空间中; 
* rseg33~128 则根据配置存放到独立undo表空间中（如果没有打开独立Undo表空间，则存放于ibdata中）共96个

每个回滚段维护了一个段头页，在该page中又划分了1024个slot(TRX_RSEG_N_SLOTS)，因此理论上最多支持94 * 1024个事务

Innodb引擎下每行记录都有三个隐藏列（其中有一个是隐藏行id,未设置聚簇索引时会根据此行建立索引，其他情况下无用）：
剩下两个字段就和MVCC有非常大的关系：

* DB_TRX_ID：6byte, 创建这条记录/最后一次更新这条记录的事务ID
* DB_ROLL_PTR：7byte，回滚指针，指向这条记录的上一个版本（存储于rollback segment里）

>其中record头信息里存储了删除标记位

实际更新一条记录时，大概就是：

先把当前版本记到回滚段的 undo log 里，再改新记录。新记录上的 `DB_TRX_ID` 会变成当前事务 ID，`DB_ROLL_PTR` 指向老版本的 undo log。这样一条版本链就出来了，后面再结合隔离级别和 read view 判断当前事务到底能看到哪个版本。

**在不同的隔离级别下的MVCC的不同表现**

* RR：read view 在第一次读时创建，后面的读都复用这个视图，所以能保证可重复读
* RC：每次读都会新建一个 read view，所以能读到别的事务已经提交的结果

所以对于InnoDB来说，RR虽然比RC隔离级别高，但是开销反而相对少。

**二级索引下MVCC如何工作**
因为只有聚簇索引才保存 `DB_TRX_ID` 和 `DB_ROLL_PTR`，二级索引本身不保存这些信息。所以如果更新操作改到了二级索引，二级索引那边通常会把旧记录打上 `delete_flag`，再插入一条新索引。

这样如果按二级索引查，就没法只靠二级索引本身判断可见性，所以还是得回到聚簇索引里再确认版本。要是碰上连续几条都不可见，就会不断回表，性能自然会差一些。

为了解决这个，二级索引里还会额外维护一个 `MAX_TRX_ID`。先拿它和 `up_limit_id` 这类边界值比一轮，能提前排掉一些不可能可见的情况；但如果这个值也不够用，最后还是得回表。

**purge操作：**
为了让 MVCC 能工作，更新和删除很多时候都不会立刻把老记录真的删掉，而是先保留版本链和删除标记。真正清理这些东西的是 purge 线程。

purge 线程自己也会维护一个 read view。只要某条记录的 `deleted_bit` 为 true，并且它对应的事务版本对 purge 线程已经完全可见，那这条记录就可以放心清掉了。
