### synchronized
三大特性:

* 原子性：确保线程互斥的访问同步代码；
* 可见性：保证共享变量的修改能够及时可见，其实是通过Java内存模型中的 “对一个变量unlock操作之前，必须要同步到主内存中；如果对一个变量进行lock操作，则将会清空工作内存中此变量的值，在执行引擎使用此变量前，需要重新从主内存中load操作或assign操作初始化变量值” 来保证的；
* 有序性：有效解决重排序问题，即 “一个unlock操作先行发生(happen-before)于后面对同一个锁的lock操作”

synchronized是一种可重入锁，作用粒度是对象，锁的是对象而非引用，可重入锁的最大作用是用来避免死锁（一个类中进入两次synchronized方法），当作用在类上时，锁的是（对象的class实例，存放到元空间中 待确认）

在实现上synchronized依赖于jvm的实现，而cas的操作则依赖于硬件层面的汇编指令

#### 作用在方法上和代码块
作用在方法上则会在方法的访问标志上加ACC_SYNCHRONIZED标志，当jvm执行到此方法的时候，便会去确认有没有此标志，有的话，就尝试获取对象的monitor锁，因为每个对象都带有一个monitor对象，所以一旦其中一个线程获取了，那么其他线程就需要等待

作用在代码块上则会在方法里代码块前后加入指令monitorenter,monitorexit两条指令，代表monitor对象的获取和释放；

二者相比的话可以看到代码块上颗粒度更小，但是两者都是去竞争monitor对象锁

#### markword 和 LockRecord
在线程进入代码块时，如果发现此时对象为无锁状态时，jvm会首先建立一个名为lock record的空间，放在当前线程的栈帧中，然后拷贝对象头中的mark word至lockrecord中，拷贝成功后，会使用cas尝试将mark word中的指针指向locakrecord的空间，并将owner指针指向对象头markword;如果成功，则设置为轻量级锁，否则失败，进行自旋，一定次数后升级为重量级锁

### 锁的优化

#### 锁消除 锁粗化
锁消除的依据是逃逸分析的数据支持，这部分由编译器进行优化，比如下面的代码
```
public void vectorTest(){
    Vector<String> vector = new Vector<String>();
    for(int i = 0 ; i < 10 ; i++){
        vector.add(i + "");
    }

    System.out.println(vector);
}
```
vector的add操作是加锁的，但jvm可以分析出vector变量没有逃离本地方法栈，其他线程不可能使用，所以这部分的加锁是毫无意义的，即可以把vector的锁消除掉；
```
Vector<String> vector = new Vector<String>();
public void vectorTest(){
    
    for(int i = 0 ; i < 10 ; i++){
        vector.add(i + "");
    }

    System.out.println(vector);
}
```
而如果vector是在外面，是共享的，那么此时就无法消除，但这样每次循环都会加锁释放锁，此时如果开启锁粗化，那么编译器可能会把synchronized提到for循环外面

参数：
-server -XX:+DoEscapeAnalysis -XX:+EliminateLocks其中+DoEscapeAnalysis表示开启逃逸分析，+EliminateLocks表示锁消除

#### 自旋锁 & 适应性自旋锁
**线程的阻塞需要cpu从用户态转化为和核心态**
>cpu提供了四个特权指令ring0-3,ring0最高，只能内核或操作系统使用，ring3最低普通的用户进程就能使用；每个ring都含有一系列指令集
>每个进程都有一个4G大小的虚拟空间（linux）,其中前3G是用户空间，最后1G是内核空间，而每个进程都存在一个内核栈，各内核栈一定是不共享的
>什么时候cpu会从用户态转化为内核态？
>发生系统调用时，通过中断机制；
>产生异常时；
>外设产生中断，当外围设备完成用户请求时，比如硬盘读写操作完成，此时会通知cpu,此时cpu会暂停当前下一条要执行的指令，如果此时用户是在用户态，那么自然变成内核态，需要转换；

为什么会出现自旋锁：
场景：大部分情况下可能对象锁只会持续很短一段时间，很少会有线程霸占着对象锁不释放，为了这很短的时间去唤醒阻塞线程是比较浪费资源的；

jdk1.4以后默认开启，且自旋次数是10，循环检测10次还没有等待到的话则应该挂起，因为自旋也是浪费cpu处理器资源的

适应性自旋锁出现场景：
自适应就意味着自旋的次数不是固定的，一般一个线程申请成功之后，那么下一次自旋的次数会增多，如果线程自旋到了此自旋的次数后那么就会升级成重量级锁，并且此线程下一次申请的时候自旋的次数会减少，所以如果某个锁很少能自旋成功，那么jvm会一直减少甚至省略自旋过程，直接膨胀；
适应性自旋锁是1.6引入的

自旋锁优缺点：
优点：减少cpu切换上下文所带来的消耗
缺点：不适应线程持有锁的时间长，这样等于一直占用cpu资源不干活；

自旋锁无法解决线程的公平性，因为多个线程自旋那么假设前面的线程自旋很多次都没成功，此时来了一个线程自旋了一次，正好锁释放，当前线程就抢占了，比如，可以看到非公平锁会先尝试获取（当然这不是自旋锁 就是举个例子）

#### 偏向锁
出现背景：
hotspot作者经研究发现 大多数情况下，锁不仅不存在多线程竞争，而且总是由同一线程多次获得，为了减小获取锁的代价，引入偏向锁
使用场景： **运行时并没有多线程竞争**
为什么没有多线程竞争还要加锁呢，这是因为很多基础库为了保证在任何条件下都不会出问题，会考虑多线程的场景，但实际使用中可能没有多线程的场景，或者很少

原理：
偏向锁只需要一次cas操作置换threadId

* 检测Mark Word是否为可偏向状态，即是否为偏向锁1，锁标识位为01；
* 若为可偏向状态，则测试线程ID是否为当前线程ID，如果是，则执行步骤（5），否则执行步骤（3）；
* 如果测试线程ID不为当前线程ID，则通过CAS操作竞争锁，竞争成功，则将Mark Word的线程ID替换为当前线程ID，否则执行线程（4）；
* 通过CAS竞争锁失败，证明当前存在多线程竞争情况，当到达全局安全点，获得偏向锁的线程被挂起，偏向锁升级为轻量级锁，然后被阻塞在安全点的线程继续往下执行同步代码块；
* 执行同步代码块；

**获得偏向锁的线程是不会主动释放锁的，需要等待其他线程来竞争**
当上面第4步时：会先暂停拥有偏向锁的线程；
然后判断锁对象是否还处于被锁定状态

* 否，则恢复到无锁状态（01），以允许其余线程竞争。允许另一个线程替换threadId为偏向锁持有者
* 是，则挂起持有锁的当前线程，并将指向当前线程的锁记录地址的指针放入对象头Mark Word，升级为轻量级锁状态（00），然后恢复持有锁的当前线程，进入轻量级锁的竞争模式；（**当前线程挂起再恢复的过程中并没有发生锁的转移，仍然在当前线程手中，只是穿插了个 “将对象头中的线程ID变更为指向锁记录地址的指针**）

一般来说，多个cpu会共享一条系统总线，靠总线来连接内存，cas是靠硬件层面来实现的，jvm只是封装了调用而已，所以cpu的某个核心调用了cas使值更新之后，会通过总线向其他核发出信号告知本地缓存失效，从而保持缓存的一致性，所以当cas很频繁时，总线通信会很频繁，所以本质上偏向锁是为了消除cas，降低cache一致性流量

获取流程：

* 先从当前的栈空间获取一个空闲的lockrecord（obj对象为null则为空闲状态）,如果能找到，继续往下走，否则重新执行；
* 将lockrecord obj指针设置成**要锁的对象**，进入下列分支判断
    * 锁对象markword是偏向模式
        * 当前偏向的线程是自己且epoch = class对象的epoch,那么直接返回成功即可，从这里可以看出，这种相当于可重入的特性，**并且每次重入都会分配lockrecord** ->success 
        * 偏向模式关闭（锁对象是开启的，但是class对象是关闭的），那么此时尝试撤销偏向锁，cas操作替换锁对象中的markword为class对象的markword
        * 比较epoch(class与锁对象)，如果不相等，则尝试重偏向，构造一个偏向自己的markword> 原笔记此处有一张配图，资源路径还没整理过来。，并尝试cas替换对象头（预期原值是上面获取的markword,新值是刚构建的），替换失败则说明多线程竞争，进行锁升级 ->success 
        * 走到这里说明，要么当前锁对象是匿名偏向（无偏向任何线程），要么偏向别的线程；构建一个匿名markword 尝试把当前markword替换，如果预期是匿名的那么就替换成功，然后继续往下；失败则进行锁升级 ->success
        >可以看出只要有多线程竞争就立马升级
    * 判断完上面的case，会有一个标志sucess ，如果失败说明没有开启偏向模式，或者偏向线程不是指向自己，下面其实是轻量级锁的逻辑了，首先构建一个Displaced Mark Word(无锁)，并将lockrecord 里的lock指针指向它；然后cas尝试将锁对象的markword替换为lockrecord，失败则判断是不是重入锁，是的话则设置lockrecord的Displaced Mark Word 为null即可（前面已经指向过markword）

可以看出如果当前**锁已偏向其他线程||epoch值过期||偏向模式关闭||获取偏向锁的过程中存在并发冲突**，都会进入到InterpreterRuntime::monitorenter方法， 在该方法中会对偏向锁撤销和升级。

>当调用对象的锁对象hash方法时，会导致锁的升级，因为偏向锁和轻量级锁没有地方存储hashcode,无锁状态存放在markword中，重量级锁存放在monitor对象中

撤销流程：
撤销的时候会判断是不是要撤销当前线程，如果是的话直接撤销即可；否则，需要放到safepoint安全点集合中等待执行

* 判断偏向的线程是否存活（jvm维护了一个集合存放所有的存活的线程），不存活了则直接撤销偏向锁即可
* 否则遍历线程中lockrecord查看是否还有obj的引用，有的话说明还在同步块中，此时进行升级，遍历所有record(可重入)，遍历结束后会留下最高的，也就是第一次获取锁的record,此时尝试将markword指向自己record，升级完成
* 否则说明偏向线程已经不再同步块中了，设置为无锁状态

释放流程：
遍历当前线程栈，将lockrecord中的obj对象置成空即可

批量重偏向（默认阈值时20个），就是当某个class的对象每次升级都会记录一次次数，当超过20次时，jvm会把class epoch加一，然后通过jvmThread更新到所有正在被使用的偏向锁对象（遍历record）,正在使用则把他们的epoch+1，不对这些进行重偏向，否则会破坏锁的安全性（因为可能已经有升级成轻量锁的对象）；但是还没被使用的则不动epoch,下次获取的时候进行比较如果不同，那么可以直接进行替换线程id,否则的话多线程冲突是必须升级到轻量级锁的

使用场景：**线程接近于交替执行的情况**
什么时候会升级成轻量级锁：
当没有开启偏向锁，或多个线程竞争偏向锁时会导致升级成轻量级锁

获取轻量级锁的过程：

* jvm先在当前线程栈帧空间中建立一个lockrecord的记录，用于存储对象目前的MarkWord的拷贝（前提是先检测到是无锁状态，偏向锁的情况下会先释放偏向锁成无锁，然后加轻量级锁）
