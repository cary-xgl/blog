## AQS 是什么

AQS 是一个用来构建锁和同步器的框架。

像独占锁、共享锁、条件队列这类能力，很多都是在它的基础上做出来的。`ReentrantLock` 就是很典型的例子。

## AQS 里的几个东西

AQS 里面有个 `Node` 内部类，队列主要就是靠它串起来。

几个常见字段：

- `waitStatus`：当前节点的状态
    - `0`：初始化状态
    - `CANCELLED(1)`：线程放弃了获取锁
    - `SIGNAL(-1)`：后继节点要挂起，等前驱节点唤醒
    - `CONDITION(-2)`：在条件队列里等待
    - `PROPAGATE(-3)`：共享模式下用
- `thread`：当前节点对应的线程
- `prev` / `next`：前驱和后继节点
- `SHARED`：共享模式
- `EXCLUSIVE`：独占模式

AQS 里还有一个关键变量：

- `state`

在独占模式下，`state > 0` 一般表示已经有线程持有锁了，而且可能重入了多次。  
在共享模式下，`state` 也可以表示剩余资源数。

独占锁场景里，AQS 的父类还会用 `exclusiveOwnerThread` 记住当前是谁持有锁。

## 子类一般要做什么

AQS 本身不直接定义“这把锁到底怎么抢、怎么放”，这些逻辑通常交给子类实现。

像 `ReentrantLock` 这种子类，会去实现独占模式下的获取和释放；如果是读写锁之类的，也可以同时实现共享和独占两套逻辑。

## 释放锁时在做什么

释放锁后，如果发现后面还有线程在等，就要从队列里找一个合适的节点唤醒。

这里一个容易漏的点是，AQS 不一定直接顺着 `next` 找。因为有些被取消的节点，`next` 指针可能已经不可靠了，但 `prev` 往往还在，所以从尾往前找会更稳一些。

## 可重入锁 `ReentrantLock`

`synchronized` 和 `ReentrantLock` 都是可重入锁。

这个特性最直接的作用，就是避免“同一线程已经拿到锁了，进到另一个也要这把锁的方法时把自己卡死”。

比较常见的场景：

- 一个 `synchronized` 方法里调用另一个 `synchronized` 方法
- 递归调用带锁的方法

如果锁不可重入，这类代码很容易把自己锁死。

## 悲观锁和乐观锁

悲观锁的例子：

- `synchronized`
- `ReentrantLock`

乐观锁最常见的例子就是 `CAS`。

CAS 就是比较并交换。它会拿三个值去做一次原子操作：

- 旧值
- 期望值
- 新值

如果旧值和期望值相等，就把新值写进去；不相等就失败。

这套东西底下靠的是 CPU 的原子指令，不是 Java 自己“模拟”出来的锁。

## `wait` / `notify`

`wait` 和 `notify` 都是 `Object` 上的方法，所以调用时一定是某个对象在调，比如 `obj.wait()`。

为什么一定要放在同步代码块里，重点不在语法要求，而是要保证状态和等待动作放在同一个锁保护下。

拿生产者消费者举例：

- 线程 1 判断 `count <= 0`
- 这时线程 2 先执行了 `count++` 和 `notify()`
- 线程 1 再往下执行 `wait()`

这样就会出现状态已经变了，但线程还睡下去的情况。

如果外面有同步块把这段逻辑包住，线程 1 在 `wait()` 之前，别的线程拿不到这把锁；只有线程 1 真正 `wait()` 了、把锁放掉了，别的线程才能进来生产数据，再去 `notify()`。

这里底下依赖的就是对象关联的 `monitor`。`wait` 的线程会进 `wait set`，被唤醒后再去竞争锁。

## `synchronized`

### 三个特性

- 原子性：同一时间只有一个线程能进同步代码
- 可见性：一个线程改过共享变量后，别的线程能看到
- 有序性：能约束一部分重排序

这里面可见性和有序性，还是靠 Java 内存模型那套规则在兜。

### 可重入

`synchronized` 也是可重入锁。

它锁的是对象，不是引用。  
如果加在类上，锁住的是这个类对应的 `Class` 对象。

### 方法和代码块

加在方法上时，字节码层面会带上 `ACC_SYNCHRONIZED` 标记。JVM 看到这个标记，就会在方法执行前尝试拿对象的 `monitor`。

加在代码块上时，字节码里会插入：

- `monitorenter`
- `monitorexit`

不管哪一种，最后争的都是 `monitor`。

### 作用在普通对象和类上

作用在普通对象上，锁的是当前对象。  
作用在 `static` 方法或类对象上，锁的是这个类对应的 `Class` 实例。

这也是为什么：

- `synchronized(this)` 和 `static synchronized` 不是一把锁
- 两者可以互不影响地并发执行

## 对象头、`mark word` 和 `monitor`

JVM 对象头里有一块很关键的数据，通常会叫 `mark word`。

这里会放很多运行时信息，比如：

- `hashCode`
- GC 年龄
- 锁标志位
- 偏向线程 ID
- 偏向时间戳

锁状态不同，这块内容也会变：

- 无锁
- 偏向锁
- 轻量级锁
- 重量级锁

如果锁已经膨胀成重量级锁，对象头里就会指向堆里的 `monitor` 对象。

## `mark word` 和 `LockRecord`

线程进入同步代码块时，如果发现对象现在还是无锁状态，JVM 会先在线程栈帧里建一个 `LockRecord`。

接着会把对象头里的 `mark word` 拷进去，再用 CAS 尝试把对象头改成指向这个 `LockRecord`。

如果成功，就拿到了轻量级锁；如果失败，要么是重入，要么就是有竞争，需要继续往上升级。

## 锁升级

锁的状态只会往上走，不会往回降：

- 无锁
- 偏向锁
- 轻量级锁
- 重量级锁

偏向锁也可以通过参数禁掉。

## 锁消除和锁粗化

这两块都和逃逸分析有关。

### 锁消除

比如下面这段代码：

```java
public void vectorTest() {
    Vector<String> vector = new Vector<String>();
    for (int i = 0; i < 10; i++) {
        vector.add(i + "");
    }

    System.out.println(vector);
}
```

`Vector#add` 本身是带锁的，但如果 JVM 能看出来 `vector` 没有逃出这个方法，那这把锁其实没有意义，就可能被消掉。

### 锁粗化

如果对象是共享的，锁消除做不了，但编译器可能会把一堆很碎的加锁操作合并一下。

比如循环里每次都要加锁、解锁，那就可能直接把锁提到循环外。

相关参数：

`-server -XX:+DoEscapeAnalysis -XX:+EliminateLocks`

## 自旋锁和适应性自旋

线程阻塞和唤醒是有成本的，尤其会牵扯到用户态和内核态切换。

所以常见做法是，先别急着挂起线程，先让它空转一会儿，看看锁会不会很快释放。这就是自旋。

### 为什么会有自旋

很多场景下，锁其实只会被占很短一会儿。  
如果刚发现拿不到锁就马上阻塞，再唤醒，反而更亏。

所以先自旋几次，有时更划算。

JDK 1.4 之后默认开了自旋，默认次数是 10 次。  
如果转了几次还拿不到锁，再挂起线程。

### 适应性自旋

自适应的意思是，自旋次数不是固定的。

如果某把锁前几次很容易靠自旋拿到，后面自旋次数就会多一点；如果老是转半天也拿不到，JVM 就会减少自旋，甚至直接跳过。

这套是 JDK 1.6 引进来的。

### 优缺点

优点：

- 少一次线程阻塞和唤醒的切换成本

缺点：

- 不适合锁占用时间长的场景
- 自旋期间会一直占着 CPU

### 公平性问题

自旋解决不了公平性。

几个线程都在转时，谁先撞上锁释放，谁就先拿到，不会因为“谁等得更久”就自动更公平。

### 几种常见的公平自旋锁思路

`TicketLock`

## 偏向锁

### 出现背景

HotSpot 这边后来发现，很多锁在实际运行里根本没有竞争，而且经常总是同一个线程反复拿。

这种场景下，每次都走 CAS 去抢锁，其实是在白白付成本，所以才有了偏向锁。

适用场景也很明确：

- 运行时基本没有多线程竞争

### 基本原理

偏向锁就是尽量把“这把锁偏向哪个线程”直接记在对象头里。

如果后面还是这个线程来拿锁，连 CAS 都省了。

流程大概是：

- 先看 `mark word` 是不是可偏向状态
- 如果已经偏向当前线程，直接进同步块
- 如果偏向别的线程，再决定是重偏向还是升级
- 如果出现真正竞争，就往轻量级锁升级

这里有个点比较关键：

**拿到偏向锁的线程不会主动释放。**  
只有别的线程过来竞争时，才会触发撤销或升级。

### 为什么偏向锁能省事

CAS 本身虽然快，但做得很频繁时，缓存一致性流量会很高。

偏向锁要解决的就是这个问题，在“基本没人抢”的前提下，把这一层 CAS 也省掉。

### 源码里的一些点

源码这块你原笔记已经记得比较细了，先抓这几个就够了：

- 锁对象和类元数据对象里都有 `epoch`
- 重偏向和批量撤销都会用到它
- 只要看到偏向别的线程、`epoch` 过期、偏向模式关闭，或者偏向过程中有并发冲突，后面都可能进撤销和升级流程

还有一个容易漏的点：

> 调对象的 `hashCode` 可能会触发锁升级，因为偏向锁和轻量级锁都没地方稳定存这个值，重量级锁的 `monitor` 才有位置。

### 撤销、批量重偏向、批量撤销

撤销偏向锁时，会先看原来的线程还活不活、还在不在同步块里：

- 线程都没了，直接撤销
- 线程还在同步块里，就升级
- 线程还活着但已经退出同步块，就恢复到无锁

如果某一类对象反复发生偏向撤销，JVM 还会做两件事：

- 批量重偏向
- 批量重撤销

默认大概是：

- 20 次左右触发批量重偏向
- 40 次左右触发批量重撤销

更直接一点说，就是 JVM 发现这类对象的偏向策略不太合适了，要重新调。

## 轻量级锁

### 适用场景

轻量级锁更适合线程接近交替执行的情况。

它不希望一上来就建 `monitor`，先试着用栈上的 `LockRecord` 把锁拿下来。

### 什么时候会升级到轻量级锁

- 没开偏向锁
- 偏向锁遇到多线程竞争

### 获取过程

获取过程大概是这样：

- 在线程栈帧里创建 `LockRecord`
- 拷贝对象头里的 `mark word`
- 用 CAS 尝试把对象头指向这个 `LockRecord`
- 成功就拿到轻量级锁
- 失败就看是不是重入，不是的话一般会继续膨胀

### 重入

重入时不会真的再去抢一遍对象头，而是靠多个 `LockRecord` 记住这几次进入。

### 释放过程

轻量级锁释放时，会尝试把 `Displaced Mark Word` 通过 CAS 写回对象头。

如果写回失败，通常说明已经出现竞争，这时候锁会继续往重量级锁走。

这里有个点比较关键：

**轻量级锁只要出现多线程竞争，就很容易升级成重量级锁。**

所以它的意义不是“能扛高竞争”，而是：

- 没竞争时别急着建 `monitor`
- 线程交替执行时，成本比重量级锁低

## 重量级锁

### 什么时候会升级过来

真正有并发竞争，前面的偏向锁、轻量级锁兜不住时，就会膨胀成重量级锁。

### 膨胀过程里几个常见分支

在 `inflate` 过程中，一般会遇到这几种情况：

- 已经是重量级锁了，直接拿 `monitor`
- 正在膨胀中，继续等
- 当前还是轻量级锁，那就初始化 `monitor`，把对象头切到膨胀状态，再完成替换
- 当前是无锁状态，也可能直接建 `monitor`

这里多一个 `INFLATING` 状态，不是多余，主要是为了让并发线程知道：这个对象正在膨胀，先别乱抢。

### 进入 `monitor` 后

膨胀完以后，会真正进 `monitor` 的获取逻辑：

- `owner == null`，CAS 成功就直接拿到锁
- 如果是重入，就增加重入次数
- 如果都不是，就先自旋
- 自旋还不行，再进等待队列

这里也就能看见 `EntryList` 和 `WaitSet` 的区别：

- 竞争锁失败的线程，一般在 `EntryList`
- 调了 `wait()` 的线程，会进 `WaitSet`

等 `notify` 或 `notifyAll` 之后，再回去竞争。
