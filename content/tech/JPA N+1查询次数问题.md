> JPA 里比较常见的一类慢查询问题
<!--more-->

## JPA 的 N+1 问题

这个问题很常见。

比如查所有用户，直接调 `findAll()`。用户实体里如果还关联了别的对象，比如：

- `OneToMany`：标签
- `ManyToOne`：用户组

这时候就容易出现 N+1。

一开始查用户列表，只会先发一条 SQL。问题在后面。如果这些关联字段又被访问到了，JPA 会继续按用户一条一条地去查关联数据。

如果一共有 `n` 个用户，那就可能变成：

- 1 条查用户列表
- n 条查用户组
- n 条查标签

这样加起来，查询次数很快就上去了。

而且麻烦不只是在这一层。比如用户组自己又关联了别的外键对象，继续访问下去，还会再往下查。

## 全改成懒加载能不能解决

把外键关联都改成懒加载，能缓一部分问题，但本质上不是解决 N+1。

它解决的是“不需要的时候别先查出来”。

比如这次其实只想拿用户基础信息，不关心标签和用户组，那懒加载不会上来就把这些数据全查出来。

但如果后面真的访问了这些关联字段，N+1 还是会出现。

## 处理方式

比较直接的一种方式是 `EntityGraph`。

它不是把实体上的默认 `fetch` 策略整个改掉，而是只对这次查询生效：使用JOIN把需要的实体一个SQL查询出来

比如查用户时，明确知道后面一定会用到用户组，可以这样写：

```java
public interface UserRepository extends JpaRepository<User, Long> {

    @EntityGraph(attributePaths = {"userGroup"})
    List<User> findAll();
}
```

这样查用户时，会把 `userGroup` 一起带出来，避免后面再按用户一条条去查用户组。

如果后面还要用到更深一层的关联，也可以继续往 `attributePaths` 里配，但这块要结合实际 SQL 看，不是配得越多越好。
