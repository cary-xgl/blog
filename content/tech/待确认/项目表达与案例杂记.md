线程池的创建有哪几种
- 一般来说不推荐用Executors.newThreadPool这种方式来创建，因为这种方式里面的线程参数等都是封装好的，所以线程的参数对其他开发同学来说可能不够清晰
- Executors.newFixedThreadPool(n) ，直接创建一个核心线程数和最大线程数相同的线程池，并且默认的队列是LinkedBlockingQueue，是无有界的，但是默认最大值是（maxInt），所以队列无限长可能导致oom,并且是一个阻塞队列，意思是取元素的时候如果没有元素的话就会一直等待， 等待队列有元素了再唤醒；放元素的时候如果队列满了就返回false插入失败，否则的话获取锁进行数据的插入，插入成功之后尝试唤醒take元素的线程; 默认的拒绝策略是default; 场景是可以比如根据cpu控制并发执行的线程数
- Executors.newSingleThreadExecutor() 新建一个核心线程和最大线程都只有一个线程的线程池，同样采用LinkedBlockingQueue，应用场景是可以保证提交任务的执行顺序，一个执行完了才会执行另一个; 生成分批记录使用此场景
- Executors.newCachedThreadPool() 核心线程数为0,最大线程数为maxint,keepAliveTime 为60s, 队列是SynchronousQueue（同步队列，基于cas），并且默认是不公平的竞争策略，公平的是队列的实现，非公平的看起来是栈？默认的keepAliveTime设置表示缓存时间
- Executors.newScheduledThreadPool(n) n为核心线程数 （newSingleThreadScheduledExecutor 默认n==1）,最大线程数不设限制，队列采用DelayedWorkQueue（无界），基于最小堆（完全二叉树）实现的阻塞无界队列，所以每次取出来的必定是先执行的（基于距今执行时间最近的堆构建），取出task的时候，查看据任务执行时间的delay,然后线程await这么久，然后再一次循环就可以执行了
    - 取出task schedule [scheduleAtFixedRate(可以设定周期，执行多少次)] 默认执行一次
    - 可以设置线程的leader，不然的话可能核心线程都在等待第一个执行，然后等待delay的时机全部唤醒，但最终只有一个能执行成功，如果有leader的话，只有leader会等待delay的时机然后执行任务，并释放锁，leader来释放信号唤醒其他线程继续争抢任务
- 上面的都是通过executors封装的几个常用的进行创建，但项目中的场景复杂多变，此时可能需要我们自定义一个线程池 通过new ThreadPoolExecutor(**corsize, maxsize, keepAliveTime,unit,queue, threadFactory, rejectedhandler**) 来自定义想要的参数，比如线程工厂，可以自定义一下namePrefix方便排查问题，rejectedHandler来帮助我们在实际的业务场景下使用不同的拒绝策略

FixedThreadPool vs CachedThreadPool
- 二者一个对同时运行的线程数没有做控制(线程也需要占用内存空间，所以同一时间大量任务过来也可能导致oom)，另外一个没有对任务做限制（可能导致oom）

线程池提交任务
- 有返回值：submit,返回一个future（继承Callable）
- 无返回值：execute 无返回值 （继承Runable）

线程池的keepAliveTime
- 主要是用来判断当线程池中活跃的线程数大于核心线程数的时候会保持这么久没任务的话就进行线程的回收，主要是通过去queue里取任务，比如上文提到的阻塞队列，那么取的时候会默认保持等待这么久，然后取不到返回null, 上层直接把此线程回收掉
- 当设置为0时，则空闲时立即结束

线程池的拒绝策略落地
- 默认的异常处理，abortPolicy 直接向上抛出RejectedExecutionException异常
- 不做处理DiscardPolicy 不抛出异常，直接丢弃任务
- 交给调用者处理，这种会阻塞调用者的后续执行等
- 可以自定义一个异常处理策略（正在运行的任务，线程池的状态，和是否发送告警邮件或者严重的打电话等一些策略，或者等待一会重新给线程池提交此任务），直接操作，或者通过事件抛出都可，我们项目中一般会直接由当前线程去执行，并且发送一封告警邮件

线程池会把内存打爆吗？会，见上面，队列过长的堆积或者线程过多的创建都可能导致oom

hashmap的坑
- 多线程下不安全
- 不支持排序（hashmap是无序的，所以读入和存取的顺序可能不一致）
- key和value 可以为null, 所以遇到get(key)时为null,此时不一定是key不存在，而是key和value都可能为null
- 最好不用可变对象作为hashmap的key, 因为采用可变对象的话，可能会改变对象的某些字段值，从而导致hashcode和equals发生变化，这样的话，此key可能永远检索不到了（改变回来是可以的）

- 只读事务和读写事务的区别（可以算作代码优化的一部分），开了之后hibernate的刷新模式变成了manual, 相当于手动把修改和新增提交到数据库中，这样的话其实对于查询来说是不需要校验上下文状态的；而如果是auto模式，也即开了读写之后的默认模式，这种每次查询，都需要去校验上下文状态（例如新增一条语句，他的父节点是X, 然后去数据库中执行查询语句，where条件是父节点等于X, 这样的话相当于要先把这条插入语句更新到数据库中才可以执行查询），查看是否有变更的语句，如果在递归或者for循环的场景下，这种累计是比较可怕的，所以开启

redis
- 缓存击穿：在某个时间点，某个热key突然到期，此时大量的请求发现redis中没有，直接打到db中去，把db击穿
    - 举例：某个秒杀key突然过期，请求全打到数据库中查询了
    - 未出现如何避免：互斥锁，先从redis中查询数据，如果不存在则进行锁住tryLock（非阻塞，获取不到返回false），然后从数据库中查询，二次校验redis是否有数据，因为可能存在**锁和查询redis**之间的时间差，如果没有数据才设置否则返回， 如果获取不到则sleep 一点时间，然后从重新调用此方法获取
    - 出现了如何解决：手动设置？
- 缓存雪崩：在某个时间点，大量key设置的过期时间相同，然后同一时间过期，造成大量缓存失效，打到db中去
    - 举例：秒杀活动的key设置的时间太短，到了时间key都失效了
    - 未出现如何避免：给这一批key不要设置同样的过期时间，可以基于时间点加个随机值，以便让key能分散过期
    - 出现了如何解决：先从前面负载均衡层看看能不能进行限流，逐步放开这个请求，因为数据库被打垮了之后，再重启依然是崩掉；或者看看之前有没有预留的接口把这部分key手动设置到redis中
- 缓存穿透：客户端同一时间大量访问数据库不存在的数据，比如id=不存在的，这时候redis中不存在，查询会穿透到数据库中
    - 举例：客户端请求了一个id为负数的，不负责规范的id特别大的数据
    - 未出现如何避免：应该多增加校验，校验客户端的数据是否符合规范，尽量保证数据是存在的；或者从redis取出来的时候就增加限制，如果取不到就默认抛异常或者其他的一些null的处理; 或者使用redis的布隆过滤器，多存储一份，只用来对查询的内容做判断存不存在，高效（但是对存在的判定有误差）
    - 出现了如何解决：这种一般不是用户层面发起的，这时候可以针对发出此请求的ip（如果来自一个或几个ip）做一些限流措施等

反射
- 反射的底层原理：正常我们使用对象时都会先了解这个类是什么，然后进行类的实例化，反射提供了一种机制，就是我并不知道要初始化的对象，但是我知道他具有某种属性，某种方法，所以可以在运行期间能获取类的信息，并能获取任何类的属性，通过操作字节码（通过类的全限定名找到这个类的class对象元数据信息，包括有哪些字段，方法等），直接通过newInstance就能获取到，触发类的实例化
- 反射的应用场景：基础框架中spring的单例bean的实例化，加载数据库的驱动也是，通过配置驱动的全限定名可以获取到驱动的信；业务场景中一般就是aop用的比较多，根据不同类的不同方法动态获取并做一些处理
- 反射的优点：运行期间获取任何类的信息，不需要事先知道类的信息，增加了代码的灵活性
- 反射的缺点：由于是运行期间动态获取的，所以实现不知道类的信息，需要去jvm方法区寻址找到这个类的信息，然后再继续进行后面的操作，非反射正常创建的类则编译期间已经知道了类的信息，自然执行的比较快

java 如何实现自旋锁？如何实现一个可重入锁
- 首先建立一个自旋类，里面基于一个原子引用《线程》对资源上锁，cas尝试将当前线程设置进去，如果设置不进去，就一直while循环，此为自旋锁
- 可重入锁，可以加个count数值，每进入一次就可以对count+1(没有多线程竞争的问题，因为锁总是被一个线程所持有)，每释放一次就减一，只到0的时候执行cas把当前持有设为null, 以便其他线程能获取

spring 事务失效的几种场景
- 抛出受检异常（非runtimeException及其子类，继承exception），受检异常是不会触发事务的回滚的，必须指定rollbackfor=Exception.class,或者指定rollbackforclass, 把异常加入进来
- 如果是在方法中手动把异常捕获掉了，并且只打印一个error日志这种，也是不会抛出异常的，除非使用事务切面支持器手动调用TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();即可回滚
- private方法默认也是不支持事务的，除非配置私有方法也支持事务

## eureka
服务注册中心：主要完成了服务的注册与发现（微服务时代下的产物，服务可能非常多）
>传统的非微服务的时代，服务的数量可能非常少，所以简单的加个nginx即可实现域名路由的解析，但微服务的时代背景下，服务的数量众多，所以服务出现问题的概率变大，并且服务众多，需要自己去做负载均衡；并且服务注册中心额外提供了心跳检测的功能以用来判断实例的存活情况等

其中集群模式是通过节点之间的相互注册来实现的，所有节点是一个平等的关系，所以eureka的集群模式满足了分布式架构下的ap，而zk是cp的，因为zk有选举者的概念，当leader节点挂掉之后，则其他的节点会来选举出新的leader，这段期间是不可用的

eureka提供了什么：
- eureka server提供了供心跳检测的endpoint, client每隔30s可以发送一次rest请求，这时候服务端收到请求后就会知道某个服务的某个实例还是存活状态，并对最后一次的存活状态进行刷新，并每隔一段时间和其他server同步（集群模式下每个server同时又是一个client）
- client可以获取server上面的服务dns映射，并可以通过ribbon制造负载均衡策略来实现对api提供方的请求
- client可以通过调用server提供的rest接口实现服务的下线

什么时候会触发自我保护生效？
短时间内有大量服务未提供正常心跳，比如当服务有85%（threshold）的节点（在几分钟内）都未出现正常心跳，这时候通常认为是网络故障，导致服务间的通信不可用，当网络股涨恢复时，即节点又正常提供心跳了，退出自动保护模式

feign：
一般的负载均衡策略：
- 随机
- 轮询
- 加权轮询（需要记录状态+预先配置权重，根据服务器的处理能力配置）
- 一致性hash
- 自定义

ribbon：
resttemplate使用时需要添加LoadBalanced注解使用，原理是增加了一个拦截器，实现服务名到ip的替换

默认当前实例不重试，如果又其他实例，获取其他实例重试一次，超时后重试
MaxAutoRetriesNextServer 1 还能获取几个server
MaxAutoRetries 0 当前

默认读取超时时间和连接超时时间都是3s
因为feign的重试和超时时间等都和ribbon有关系，所以默认关闭feign重试次数，超时时间大于ribbon的（应该没什么用？只要保证比ribbon加起来的大就行）

而feign使用的话，是默认使用ZoneAwareLoadBalancer进行负载均衡，默认根据zone分组，如果只有一个zone的话，那么就调用上层lb,默认是轮询，如果是多个zone的话，相当于维护一个map，每次选择最优先的zone,选不到的话从map的其他里面再取，我们项目中一般就是用这个默认策略

hystrix：通过配置feign注解的fallback
- 超时时间：(1 + MaxAutoRetries) * （1 + MaxAutoRetriesNextServer）*  ReadTimeOut < hystrix 的 timeoutInMilliseconds*

超时时间必须要符合上面的计算，不然的话未重试完成就被熔断了

- circuitBreaker 断路器：
    - enabled: 开启
    - requestVolumeThreshold: 10次# 窗口期20s内，使断路器跳闸的最小请求次数
    - errorThresholdPercentage: 60           # 失败百分比的阈值，超过则跳闸，进行降级
    - sleepWindowInMilliseconds: 5000        # 断路后多久尝试恢复，断路器打开一段时间，自动进入“半开”状态，此时，断路器可允许一个请求方法服务提供者，如果请求调用成功，则关闭断路器，否则继续保持断路器打开状态。
