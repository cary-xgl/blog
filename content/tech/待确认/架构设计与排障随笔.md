## 外部交互设计原则：

- 和第三方交互对于时间格式的，建议使用字符串交互，而不是日期，否则可能会产生时区的问题，会造成问题排查不必要的复杂度

## insight 代码设计随笔
- 对于前端或其他外部交互的接口（含有requestBody）,因为insight内部一般都会经过两步，校验及处理业务，所以比如对于部分需要根据id查询实体的（尤其需要处理opt的这种），可以根据requestBody增加一个transfer对象（校验的过程中将对应的业务对象填充进来），这样处理业务的过程可以避免对实体进行二次查询，及二次opt判断

## 线上问题排查记录
**Cpu 使用100%**
事故产生原因：scheduler模块数据资产的扫描由于需要扫描全表,并且标签的量级非常大（几十万条），在对标签的循环判断时，displayDirectory函数需要查询数据库的一个配置项，如果放到循环体内部，则每个标签都需要查一次，造成cpu吃满
```java
  private String generateReport(List<Traits> traitsList) {
    if (CollectionUtils.isEmpty(traitsList)) {
      return "0,0";
    }
    Map<Boolean, List<Traits>> sumMap = traitsList.parallelStream()
        .collect(Collectors.partitioningBy(t -> TraitsType.DIRECTORY.equals(t.getType())));
    Map<Integer, List<Traits>> levelTraitsMap = traitsList.stream()
        .filter(t -> displayDirectory || t.getStatus().equals(Status.ENABLE))
        .collect(Collectors.groupingBy(t -> getTraitsLevel(traitsCommonService.getAncestors(t))));
    int maxLevel = levelTraitsMap.keySet().stream().max(Comparator.naturalOrder()).orElse(1);
    List<String> numbers = IntStream.rangeClosed(1, maxLevel)
        .map(level -> Optional.ofNullable(
            levelTraitsMap.get(level).stream()
                .filter(traits -> level == 1 || displayDirectory() ||
                    !TraitsType.DIRECTORY.equals(traits.getType()))
                .collect(Collectors.toList()))
            .map(List::size).orElse(0))
        .mapToObj(String::valueOf)
        .collect(Collectors.toList());

    return String.format("%d,%d,%s", sumMap.get(Boolean.TRUE).size(),
        sumMap.get(Boolean.FALSE).size(), String.join(",", numbers));
  }

  private Boolean displayDirectory() {
    return configCommonManager.getConfigBooleanValue("WEB_TRAITS_ASSETS_DISPLAY_DIRECTORY");
  }
```
排查过程：

1. 进入容器内部执**top**命令，查看所有进程占系统CPU的排序，PID那一列就是进程号，找到cpu异常的进程（比如pid=7）
2. 执行**top -Hp 7**命令,此命令用来查看java pid进程下的所有线程占CPU的情况,比如线程pid=10
3. 因为线程的堆栈日志中保存的都是16进制数据，所以执行“printf "%x\n 10"命令把线程id是10转化为16进制； 打印：a，那么在jstack中线程号就是0xa
4. 执行**jstack 7 | grep -C30 "0xa"**  查找7这个进程下-》线程ID（jstack堆栈信息中的nid）=0xa的线程状态。打印前后30行数据，可调整显示的行数，经查找堆栈日志定位到此函数displayDirectory异常，查看业务代码猜测是此原因，本地调试确认此问题

解决方案：displayDirectory()函数提到外层，或者对配置项的查询增加缓存即可，保证只查询一次即可（选择提到外层），修复后的代码如下：

**Queue Processor OOM：**
事故产生原因：
数据使用概览调用了一个hql语句如下，因为hibernate内部会维护查询计划的缓存（query plan cache memory）,并且hibernate对于in条件的处理策略有点暴力，比如图上的语句传递了一个in条件，那么in条件的集合传不同数量的值，jpa会缓存多次，并且这个查询语句每一个的缓存是100M左右，所以如果传递了n个查询语句，并且每个查询语句in条件数量不同，那么最后的缓存可能是n*100M，所以如果连续传递这部分的查询语句，最后的结果就是内存暴涨，并导致oom
> 原笔记此处有一张配图，资源路径还没整理过来。

而数据使用概览的场景：会对最近30天的日期每天创建的标签查询latestuv或者alluv，所有一次调用数据使用概览就会触发30*2（alluv和latestuv各一次）*100M的缓存（每天创建的标签数量几乎不相同），并且这部分是jpa维护着的大对象，会进入到永久代，无法被full gc回收调，并且代码里hql语句很少，导致这部分其实不会被其他最新的hql查询覆盖掉，所以会一直引用着，所以第二天调用数据使用概览的时候前29天会命中查询计划的缓存，由于标签的一些停启用或者取消共享等会操作，可能前29天的有部分也不会命中缓存，基本上会稳定新增200M+，所以调大内存不能解决根本问题，总有一天会爆掉
>hql的默认缓存数量: hibernate.query.plan_cache_max_soft_reference=2048

排查过程：
- 先观察服务的日志，发现最后的错误是oom-》内存爆了
- 经看日志，发现数据使用概览的任务日志只有start，没有end，猜测是在数据使用概览出的错（并且后面有复现）
- review 数据使用概览的日志，推测可能是使用的大对象导致的，后否定，原因是系统中类似的map结构不算少，如果是因为这个oom，那么其实都会oom
> 原笔记此处有一张配图，资源路径还没整理过来。
- 后重启后通过后台接口不断触发数据使用概览，并观察gc情况，发现在12G内存的情况下，max(近10G)，经过触发几次（date不一样）后台接口，发现永久代增长很快，并且很快就到达了顶点，此时会自动触发full gc（大约是一分钟之内触发的次数），发现完全回收不掉这部分内存，导致oom(猜测哪里内存泄露了)
> 原笔记此处有一张配图，资源路径还没整理过来。
- 代码层面看不出来，需要导出堆栈日志**jmap -histo:live**，然后使用jprofiler等工具分析内存使用情况（日志文件是8G，max75%时导出来的堆栈），直接查看大对象发现queryplancache占用较高，去查找相关资料（
https://stackoverflow.com/questions/31557076/spring-hibernate-query-plan-cache-memory-usage 
），去代码中查看@query的hql语句，定位到原因中提到的语句，至此排查结束
> 原笔记此处有一张配图，资源路径还没整理过来。

解决方案：
两种办法
- 调小hql的默认查询计划缓存数量（hibernate.query.plan_cache_max_soft_referenc）改为比如几十，这样的话那么会导致几乎很少会命中缓存，但其实也可以解决问题，并且这部分场景也不需要进缓存
- 设置参数：hibernate.query.in_clause_parameter_padding: true；此参数的作用是比如有几条查询语句的in参数分别是（3，4，5，6，7，8），设置为false会导致缓存7次，而设置为true则只会缓存两次，因为会自动填充（比如n个参数，则n会与2的幂次方进行比较，向上找到一个最小的幂次值，并把不够的参数个数默认填充，这样就会极大的缩小缓存数量），这样几乎10来次就能解决这个缓存问题
- 不使用hql语句或者不使用in（比如使用any）（都需要改代码适配）
最终采用第二种

事故复盘：
hibernate真的是太复杂了，功夫不到家！
