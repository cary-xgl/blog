> 记几个和数据库批量交互有关的优化点，主要还是 Spring Data JPA 这一套里容易踩的地方。
<!--more-->

基于 Spring Data JPA 框架

### For 循环优化

代码里很常见一种写法：`for` 循环里反复 `findOne`。

这种场景一般都可以先把 ID 收起来，直接 `findAllById` 批量查，再转成 `map` 来用。  
这样能少很多次数据库往返，查找总时间和时间复杂度都会好一些。

### 报表覆盖式入库时的多次重算重入

这类场景一般都会先把旧数据删掉，或者打状态位软删。  
如果后面又碰到重复数据，再把状态恢复回来。

这里有个坑：如果直接用 Spring Data JPA 的派生查询去删，比如：

```java
deleteByReportDate(Date reportDate);
```

这个名字看起来像是一条删除语句，但实际不一定。

JPA 这里很可能会先按 `reportDate` 把所有符合条件的数据查到内存里，再一条一条按主键删。  
报表数据量一大，这种删法会非常慢。

如果改成 HQL 或 native SQL，行为才更接近我们预期，就是直接发一条删除语句：

```java
@modify
@query("delete table where reportDate = ?1")
deleteByReportDate(Date reportDate);
```

这种场景下，关键不是“能不能删”，而是注意别让 ORM 偷偷把它拆成逐条操作。

### `LOAD DATA`

单表入库如果只看性能上限，`LOAD DATA` 还是很猛。它本质上是直接把文件加载进去，少掉了大量网络交互。

不过这里有个点很重要： 如果文件里的数据顺序没有按索引字段排好，性能提升可能没有想象中那么大，甚至和普通 batch insert 拉不开明显差距。所以预排序这一步很重要，这会直接影响索引重建的速度。

`LOAD DATA` 这套方式的一个问题是：

- 字段特别多的时候，效果可能没那么夸张
- 这个还得结合实际表结构再测

目前字段数在十几个左右时，效果还可以。

另外，`LOAD DATA` 一般在 MyISAM 引擎下会更激进一些：
